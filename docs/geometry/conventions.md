# Geometry conventions

This page is section 1 of [ADR 0017](../adr/0017-geometry-conformance.md). It has one section per dataset. Each row is one frame transform or one box quantity, with two columns side by side.

- **What the source says** comes from the dataset's own paper, documentation or official code. Each cell names a source key (listed per section) and a locator. Every cited claim in the dataset sections was checked against the cited text. The generic section's source is the repository's own spec, which was read directly and not cite-checked. A claim the check found only partly supported is marked "partly:" with the caveat. A fact that no source settles is **unverified**.
- **What the adapter does** comes from the adapter, with the manifest key or the function it was read from. Manifest keys are in `coperceive/adapters/builtin/<name>.yaml`. Builder functions are in `coperceive/adapters/build.py` (`ManifestAdapter._poses`, `_sensor`, `_box`, `_lidar`, `_remap_points`, `_rotation`). Decoders are in `coperceive/adapters/rotation.py` (`euler_to_se3`, `matrix_to_se3`, `AxisRemap`, `Reflection`, `remap_transform`).
- A row where the two columns differ, or where the source is unverified, has a **finding**. It is a finding before any test runs.

The source column was read from documents and code. Rows whose finding says **checked on real data (N frames)** were also probed on real frames with `scripts/verify/conventions_probe.py`; the per-frame verdicts are in [pull request 166](https://github.com/adarsh-nl/coperceive/pull/166). No other row was checked against a real dataset file.

Notation:

- `A_from_B` maps B coordinates to A coordinates: `p_A = R p_B + t`. In a manifest, `direction: child_to_parent` means the file holds `parent_from_child`.
- `Rx`, `Ry`, `Rz` are the standard right-handed rotations acting on column vectors: `Rz(a) = [[c, −s, 0], [s, c, 0], [0, 0, 1]]`, `Ry(a) = [[c, 0, s], [0, 1, 0], [−s, 0, c]]`, `Rx(a) = [[1, 0, 0], [0, c, −s], [0, s, c]]`. With these, `Ry(+a)` tips `+x` toward `−z`.
- `M = diag(1, −1, 1)` is the y reflection of [ADR 0012](../adr/0012-left-handed-sources.md): `p' = M p`, `R' = M R M`. It turns `Rz(a)` into `Rz(−a)`, keeps `Ry(a)`, and turns `Rx(a)` into `Rx(−a)`.
- Schema frames ([format.md](../spec/format.md), "Axis conventions"): body x forward, y left, z up (FLU), metres; camera x right, y down, z depth (RDF); lidar uses the body axes. format.md names the world frame but gives no axes for it (its normative checks are stated in a right-handed frame). body x forward, y left, z up (FLU); camera x right, y down, z depth (RDF); lidar uses the body axes.

## V2XSet

Adapter: `v2xset.yaml`. It differs from `opv2v.yaml` only in the adapter name, the licence text, the `clock.scale_note` and `streams.boxes.fill.reason` strings, `params.split.allowed: [train, validate, test]` and `agents.discover.types: {"-1": infrastructure}`. OpenCOOD says V2XSet's label format is nearly the same as OPV2V's (OC-INTRO, "V2XSet"), and its loader reads both (OC-CODE `basedataset.time_delay_calculation`: "the data is 10 hz for both opv2v and v2x-set"). Every OPV2V row therefore applies to V2XSet, findings included, except the split-name part of OPV-17's finding: V2XSet's splits are train, validate and test, and the adapter allows exactly those. V2X-3 and V2X-4 replace the source column of OPV-15 and OPV-16 for V2XSet. The rows below add to them.

Sources: those of OPV2V, and V2X-ViT: "V2X-ViT: Vehicle-to-Everything Cooperative Perception with Vision Transformer", arXiv:2203.10638.

## Findings by effect

A file written as the source documents it would fail to load, or load nothing, at: V4R-4 (4×4 `lidar_pose`), DAIR-1 (pairing by stem, complemented tree), DAIR-5 (nested `lidar_to_novatel`), DAIR-8 (`binary_compressed`, if the release uses it), GRF-3 (no `timestamp` key), GRF-8 (`.bin`), GRF-14 (no `map_name`, `cruise_altitude`), V2X-2 (a roadside unit without `camera*` blocks, if the release has one), OPV-17 (split name, five-digit names), V4R-11 (`validate` split, if the release has one).

Geometry would move at: OPV-6, OPV-13, V4R-4 (flat pose) and V4R-6 (sign of pitch and roll), OPV-7 (camera pose inverted), OPV-12 (centre offset turned by the sign-flipped rotation of OPV-13; unrotated in the OpenCOOD loader), V4R-8 (rotated centre offset), V4R-1 and V4R-2 (mirror, unverified), V4R-7 (box frame), DAIR-7 (infrastructure offset), DAIR-10 (length and width swapped, heading −90°), DAIR-11 (tilt dropped), GEN-10 (points not reflected), GEN-6 (demo clouds moved by their agent's pose), GRF-7 and OPV-2 (frame of the points; for OPV-2, if the release predates CARLA 0.9.10).

## What the conformance suite measures

`tests/test_geometry_conformance.py` writes one synthetic world in each dataset's layout with an exporter written from the source column only, ingests it, and checks frames, sensor poses, boxes, LiDAR returns, cross-agent registration and camera projection ([ADR 0017](../adr/0017-geometry-conformance.md)). Each dataset has a case under the readings the sources support best and a case under the readings or layout its adapter reads. The second passes for every dataset, so each adapter is consistent with itself; the first carries the differences above as `xfail(strict=True)`.
