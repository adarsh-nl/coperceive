# Demo (synthetic)

The demo is a scene Coperceive generates. It is not a recording and not a download. The generator writes two vehicles, `cav-a` and `cav-b`, and one roadside unit, `rsu`, then ingests that tree and scores a synthetic prediction run. Use it to view a scene and try evaluation without a third-party dataset.

## What it contains (measured, seed 0)

A four-way junction with two CAV agents (`cav-a`, `cav-b`) and one roadside unit
(`rsu`). Ten annotated actors move for 10 s at 10 Hz: four cars, a cyclist and
five pedestrians. The junction is dressed like the product-tour captures:

- two rows of **buildings** down each side of both roads (16 blocks);
- **street trees** along both pavements (52 trunks and 52 crowns);
- **parked cars** along the kerbs (12), plus four signal poles and four kerbs;
- denser ray-cast **LiDAR** that sees both the annotated actors and that street
  furniture: 64 azimuth × 16 elevation beams over 70 m, 25 % deterministic
  dropouts and 1.5 cm beam noise. Measured on seed 0: **681 points per sweep
  (median; 519 min, 752 max, 202,826 points total** across 3 agents × 100
  frames), versus 306 in the previous demo;
- **camera** renders from the same world description: procedural sky, roads,
  pavements, lane markings and painter-sorted, light-shaded 3-D boxes for the
  actors and the street furniture. Both CAVs render 512 × 384 front cameras with
  the pinhole intrinsics recorded in `scene.yaml`; frames are palette-quantised
  PNGs (median 4.5 KB).

The layout is the generic multi-view format from
[`docs/spec/generic-multiview.md`](../spec/generic-multiview.md):

```text
<dir>/
  raw/scene.yaml + agents/<id>/{poses.csv,boxes.csv,lidar, camera}
  scenes/demo-junction/     # ingested schema-1 scene
  predictions/demo/         # run.json, boxes.parquet, predictions.jsonl, metrics
```

`create` runs the real `generic` adapter and ingests the scene, then scores the
simulated predictions with the existing evaluator. The score is a demo
self-check, not a model result and must not be presented as one. The point-cloud
files are float32 `.bin` (x, y, z, intensity); camera images are PNG.

## What Coperceive reads

The numbers here are the generator's constants, not a published dataset.

| | |
| --- | --- |
| Agents | `cav-a` and `cav-b` (`role: vehicle`) and `rsu` (`role: roadside unit`) |
| LiDAR | `{frame:06d}.bin` for all three agents |
| Cameras | `front` PNG for `cav-a` and `cav-b` only. `rsu` has no camera in the written `scene.yaml` |
| Boxes and classes | Per-agent `boxes.csv`. The generator's actors use categories `car`, `cyclist`, and `pedestrian` |
| Maps | No map key in the written `scene.yaml` |
| Timestamps | `frame_rate_hz: 10` and `frame_count: 100` |

## Expected folder layout

From `create` and `_write_agents` in `coperceive/demo/generate.py`:

```text
/data/demo/
  raw/scene.yaml
  raw/agents/cav-a/{poses.csv,boxes.csv,lidar,camera}
  raw/agents/cav-b/{poses.csv,boxes.csv,lidar,camera}
  raw/agents/rsu/{lidar}
  scenes/demo-junction/
  predictions/demo/
```

`rsu` uses `fixed_pose` and has no `poses.csv`.

## Open it in Coperceive

**Open the demo** on the library or on Get Data. Or:

```bash
coperceive demo create /data/demo
coperceive validate /data/demo/scenes
coperceive eval run demo --root /data/demo/scenes
coperceive serve --root /data/demo/scenes
```

`demo create` takes the directory and an optional `--seed` (default 0). `eval run` takes the run id `demo`, which is `RUN_ID` in the generator. The metrics it writes are the generator's self-check.

## LiDAR coordinate frame

Each sweep is written in the **recording agent's body frame**. The generic
format's LiDAR sensor declares no `body_from_sensor` in the demo, so its sensor
frame *is* the agent body frame; the app maps a stored point through the agent
pose once (`world_from_body @ body_from_sensor`). Earlier demo versions wrote
world-frame points into that slot, so the app applied the pose a second time:
both vehicles' clouds landed about 25 m off and `cav-b`'s cloud was also turned
90°. The demo test now reads the sweeps the way the app does and checks that
≥ 95 % of the object returns land inside their world boxes, and that both CAVs'
car-surface points agree in world space.

## Provenance

`create` writes `generator: "coperceive demo"` and `dataset_id: "demo"` into the
scene's `COMPLETE.json`. The result-bundle viewer uses that marker to allow
including the synthetic sensor bytes when a bundle is exported.

## Budget and speed

The generated tree is synthetic and must stay under **15 MB**. Measured for
seed 0 on this Apple Silicon machine: **12,986,276 bytes (13.0 MB)**, of which
4.3 MB is the raw tree, 4.2 MB the ingested scene and 4.5 MB the simulated
prediction run. The scene folder alone (`scenes/demo-junction`, what the Library
shows) is **4.2 MB**.

Generation (write → ingest → score) measured **12.9 s warm on Apple Silicon**
(24.7 s on a first cold run) and **7.9 s on the GitHub Actions CI runner**
(Python 3.12, run 43903069191). The demo is deterministic for a given seed:
two runs on the same machine are regenerated byte-for-byte (the size differs by
a few KB between platforms because of parquet/PNG metadata, not contents).

## Known issues and conventions

- The spec does not name the LiDAR point frame. The demo writes body-frame points
  (the app applies the agent pose once), so GEN-6 is fixed here; the spec gap
  remains. See [GEN-6](../geometry/conventions.md#gen-6) (draft, PR #166).
- Intensity in the `.bin` file is dropped. See [GEN-7](../geometry/conventions.md#gen-7) (draft, PR #166).
- Whether box `x, y, z` is the centre: **unverified** in the generic spec. See [GEN-8](../geometry/conventions.md#gen-8) (draft, PR #166).
- Box length axis and the zero of `yaw_deg`: **unverified**. See [GEN-9](../geometry/conventions.md#gen-9) (draft, PR #166).
- `handedness: left` does not reflect LiDAR points. The demo writes `handedness: right`. See [GEN-10](../geometry/conventions.md#gen-10) (draft, PR #166).
