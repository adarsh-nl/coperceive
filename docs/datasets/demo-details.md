# Demo (synthetic) — details

The short page is [Demo (synthetic)](demo.md).

`coperceive demo create <dir>` (or `coperceive.demo.create(path, seed=0)`) writes a
small cooperative scene for first-run demos. Everything is generated by
Coperceive's own code under Apache-2.0; it contains **no third-party assets and
no real dataset frames**.

## What it contains

A four-way junction with two CAV agents (`cav-a`, `cav-b`) and one roadside unit
(`rsu`). Ten annotated actors move for 10 s at 10 Hz: four cars, a cyclist and
five pedestrians. The junction is dressed like the product-tour captures: 16
buildings, 52 street trees (trunk + crown), 12 parked cars, four signal poles and
kerbs. The street furniture is ray-cast into the LiDAR and rendered into the
cameras, but it is **not annotated**. Ground truth boxes are written for every
annotated actor and agent, plus a noisy simulated prediction set with a few
misses.

- **LiDAR:** 64 azimuth × 16 elevation beams over 70 m, 25 % deterministic
  dropouts and 1.5 cm beam noise. Measured for seed 0: **681 points per sweep
  (median; 519 min, 752 max, 202,826 points total** over 3 agents × 100 frames);
  the previous demo had 306 points per sweep. Sweeps are float32 `.bin`
  `(x, y, z, intensity)`.
- **Cameras:** `cav-a` and `cav-b` render 512 × 384 front cameras with the
  pinhole intrinsics recorded in `scene.yaml`: procedural sky, roads, pavements,
  lane markings, and painter-sorted, light-shaded 3-D boxes for the actors and
  the street furniture. Frames are palette-quantised PNG (median 4.5 KB).

The layout is the generic multi-view format from
[`docs/spec/generic-multiview.md`](../spec/generic-multiview.md):

```text
<dir>/
  raw/scene.yaml + agents/<id>/{poses.csv,boxes.csv,lidar, camera}
  scenes/demo-junction/     # ingested schema-1 scene
  predictions/demo/         # run.json, boxes.parquet, predictions.jsonl, metrics
```

`rsu` uses `fixed_pose` and has no `poses.csv`.

`create` runs the real `generic` adapter and ingests the scene, then scores the
simulated predictions with the existing evaluator. The score is a demo
self-check, not a model result and must not be presented as one.

## LiDAR coordinate frame

Each sweep is written in the **recording agent's body frame** (the generic
format's LiDAR sensor has no `body_from_sensor` in the demo, so sensor frame is
body frame). The app maps a stored point through the agent pose once
(`world_from_body @ body_from_sensor`). Earlier versions wrote world-frame points
in that slot, so the app applied the pose a second time: every cloud was about
25 m off and `cav-b`'s was also turned 90°. `tests/test_demo_scene.py` reads the
sweeps the way the app serves them (`coperceive.viewdata.world_points`) and
checks that ≥ 95 % of the object returns land inside their world box for every
agent, plus cross-agent world alignment.

## Provenance

`create` writes `generator: "coperceive demo"` and `dataset_id: "demo"` into
`scenes/demo-junction/COMPLETE.json`. The result-bundle viewer uses that marker
to allow including the synthetic sensor bytes when a bundle is exported.

## Budget and speed

The generated tree is synthetic and must stay under **15 MB**. Measured for seed
0 on this Apple Silicon machine:

| | bytes | size |
| --- | --- | --- |
| full demo tree | 12,986,276 | 12.4 MiB / 13.0 MB |
| `raw/` | 4,304,689 | 4.1 MiB |
| `scenes/` (the scene folder the Library shows) | 4,202,815 | 4.0 MiB |
| `predictions/` | 4,478,772 | 4.3 MiB |

Generation (write → ingest → score) took **11.8 s warm** on Apple Silicon
(24.7 s on the first cold run). On the GitHub Actions runner the same generation
took **7.9 s** (Python 3.12, measured with the demo test in run 43903069191).
Both are deterministic for a given seed: two runs on the same machine are
regenerated byte-for-byte. The size differs by a few KB between platforms
because of parquet/PNG metadata, not scene contents.
