# v0.1.0 release checklist

Every check below says how it is verified: a CI job and step, an e2e step id
(printed as `Step … verified:` in that job's log), a test, or a manual step with
its expected result. A release needs every row green or explicitly waived by
Adarsh. Agents never tag, merge or publish a release; Adarsh does.

| id | check | how |
| --- | --- | --- |
| R1 | First run with an empty library | CI up to the network, then manual |
| R2 | Updater from a test tag | CI (config and banner), then manual with two test tags |
| R3 | Cluster datasets on the real HPC | CI over a fake ssh, then manual on the HPC |
| R4 | `feat/m2-import` merges into `main` | `gh pr checks 93` and `git merge-tree` |

## R1. First run with an empty library

**Goal.** A new user, with no Terminal, goes Get data → Griffin → "One scene
with images". Town03-000 then opens with its camera images and the map.

### In CI (before the network)

| what | where |
| --- | --- |
| The catalog offers Griffin "One scene with images" (`one-scene`, opens Town03-000, all nine camera archives, no instance segmentation, terms required) | `test (3.x)` → Run pytest → `tests/test_release_first_run.py::test_the_catalog_offers_one_scene_with_images_for_town03` |
| The dry-run measures exactly that preset's archives from the host listing (a fake host, no network), says the terms are not yet accepted, and writes nothing (no download, no acknowledgement, no `~/coperceive-data`) | `tests/test_release_first_run.py::test_the_dry_run_measures_exactly_the_presets_archives` |
| Confirming without the licence tick downloads nothing; the app's message is "Tick the Griffin licence acknowledgement, then try the download again." | `tests/test_release_first_run.py::test_confirm_without_accepting_the_terms_downloads_nothing` |
| The real app: Get Data → catalog → Griffin preset → dry-run panel → licence tick → Start Download, then Pause, Resume and Cancel (a local fake job instead of the network) | `desktop-macos` → Run Real-App macOS UI E2E Test → **Step 5b**, **Step 5e** (the e2e uses the Dev tier preset) |
| The packaged app ships the viewer bundle | `desktop-macos` → Verify packaged app ships the viewer bundle |

### Manual (needs the network, about 20 GB, which the dry-run shows)

The test uses a temporary home, so it can't read or write your
`~/coperceive-data`, your `state.json` or your Griffin acknowledgement. The
Terminal is only used to start the app this way. Everything under test happens
inside the app.

1. Install the build under test: open the release dmg, drag Coperceive to a
   folder (not over an installed copy if you want to keep it), right-click →
   Open the first time.
2. Start it with an empty home:

   ```bash
   export TEST_HOME="$(mktemp -d /tmp/coperceive-first-run.XXXXXX)"
   HOME="$TEST_HOME" "/Applications/Coperceive.app/Contents/MacOS/Coperceive"
   ```

   **Expected:** the main window opens on an empty Library ("no scenes yet"
   style message, no error).
3. Get Data → Griffin → **One scene with images**.
   **Expected:** a size panel with the download and disk size measured from
   the dataset host, the free space, and a licence acknowledgement checkbox.
   Start Download is disabled until the box is ticked.
4. Tick the acknowledgement → Start Download.
   **Expected:** the progress goes through download, convert, thumbnails and
   validate. Pause/Resume work. It ends with "Imported N scene(s)".
5. **Expected:** Town03-000 opens in the viewer by itself, or after one click on
   its Library card. Lidar, boxes and the camera strip all show images.
6. On the Town03-000 Library card, click **Download map for Town03 (CARLA
   0.9.15, CC-BY)**.
   **Expected:** the card shows the map installed. Reopening the scene draws
   the lane map.
7. **Expected, checked in the Terminal afterwards:**
   - `ls "$TEST_HOME/coperceive-data"` holds Town03-000 (and the other scenes
     of the download), `.raw/griffin` and `maps`.
   - `ls ~/coperceive-data` is unchanged from before the test.
8. Clean up: quit the app, then `rm -rf "$TEST_HOME"`.

## R2. Updater from a test tag

### What a tag builds today (`.github/workflows/release.yml`, on tags `v*`)

1. It builds the viewer bundle and bundles the Python runtime.
2. `scripts/desktop/sync_version.sh` sets `tauri.conf.json`'s `version` to the
   tag without its `v` (`git describe --tags --exact-match`). Without a tag on
   the commit, it uses `pyproject.toml` (0.1.0).
3. It turns on `bundle.createUpdaterArtifacts`, in the CI workspace only, and
   fails if `TAURI_SIGNING_PRIVATE_KEY` is missing.
4. `scripts/desktop/build_dmg.sh` builds the dmg, `Coperceive.app.tar.gz` and
   `Coperceive.app.tar.gz.sig`.
5. It checks that the packaged app ships the viewer bundle.
6. `scripts/desktop/write_latest_json.py` writes `latest.json`
   (`darwin-aarch64` → `https://github.com/adarsh-nl/coperceive/releases/download/<tag>/Coperceive.app.tar.gz`
   plus the signature). It refuses a tag that differs from the bundle version.
7. A GitHub Release `<tag>` is created with the dmg, archive, signature and
   `latest.json`, with `prerelease: false`, so it becomes "Latest".

The app polls
`https://github.com/adarsh-nl/coperceive/releases/latest/download/latest.json`
(`src-tauri/tauri.conf.json`). It does this on launch and every 6 hours while
Settings → Automatically download updates is on, and on Help → Check for
Updates….

### In CI

| what | where |
| --- | --- |
| A test tag becomes the bundle version, and `latest.json` names that version and the tag's archive URL | `tests/test_release_pipeline.py::test_a_test_tag_becomes_the_bundle_version_and_names_latest_json` |
| An untagged build reports 0.1.0 | `tests/test_release_pipeline.py::test_an_untagged_build_reports_the_pyproject_version` |
| The app polls exactly the file the workflow uploads; updater artifacts are only on in the release build; releases are not prereleases | `tests/test_release_pipeline.py::test_the_app_polls_the_file_the_release_uploads` |
| `latest.json` refuses a mismatched tag and a missing or empty signature | `tests/test_write_latest_json.py` |
| The banner, Later, Restart, a quiet 404 in the background, "You're up to date" on a manual 404, and a bad signature refused (not installed) | `desktop-macos` → Real-App macOS UI E2E → **Step 5d** (a mock `latest.json`; no install) |
| The committed config has no insecure transport | `desktop-macos` → Run Rust unit tests → `updater::tests::test_tauri_conf_has_no_insecure_transport_protocol` |

### Manual (Adarsh tags; two test tags, see gap G1)

1. Check that the `TAURI_SIGNING_PRIVATE_KEY` and
   `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` secrets are set (Settings → Secrets
   and variables → Actions).
2. Tag `v0.1.0-rc.1` on a commit whose CI is green, and push the tag.
   **Expected:** the Release workflow succeeds. The release `v0.1.0-rc.1` is
   marked Latest and has `Coperceive_0.1.0-rc.1_aarch64.dmg`,
   `Coperceive.app.tar.gz`, its `.sig` and `latest.json`. Running
   `curl -sL https://github.com/adarsh-nl/coperceive/releases/latest/download/latest.json`
   prints `"version": "0.1.0-rc.1"`.
3. Install rc.1 from its dmg (right-click → Open the first time). Help →
   About shows `v0.1.0-rc.1` as the build (see gap G3 for the version field).
   Help → Check for Updates says up to date.
4. Tag `v0.1.0-rc.2` on a **later** commit (gap G2) and push it.
   **Expected:** the release `v0.1.0-rc.2` is Latest, and its `latest.json`
   says `0.1.0-rc.2`.
5. Quit and relaunch the installed rc.1, or use Help → Check for Updates.
   **Expected:** the banner "coperceive 0.1.0-rc.2 is ready. Restart to
   update." appears, with What's new, Restart now and Later. Later hides it
   and leaves the app running.
6. Click Restart now.
   **Expected:** the app downloads, verifies the signature, replaces itself
   and relaunches. Help → About shows `v0.1.0-rc.2`, and Check for Updates
   says up to date.
7. **Revert.**
   - Delete the releases `v0.1.0-rc.2` and `v0.1.0-rc.1` and their tags in
     the GitHub UI. With no release left, `latest.json` returns 404. The app
     treats that as "You're up to date" on a manual check and stays quiet in
     the background (Step 5d).
   - An installed rc build is not downgraded. It updates to `v0.1.0` when that
     is released, because 0.1.0 sorts above 0.1.0-rc.N.
   - To withdraw a bad release while an older one exists, mark the older
     release as Latest instead of deleting it.

### Gaps found in today's code

- **G1. An rc tag is not newer than 0.1.0.** Every build that is not at a tag
  (CI artifacts, local builds) reports 0.1.0, and semver puts `0.1.0-rc.1`
  below `0.1.0`. So no such build will ever be offered rc.1. The test has to
  start from an installed rc build, hence two tags (rc.1 installed, rc.2
  offered).
- **G2. Two tags on one commit.** `sync_version.sh` uses
  `git describe --tags --exact-match`, which returns only one of them. If rc.2
  is tagged on the same commit as rc.1, the bundle can report the wrong
  version and `write_latest_json.py` then fails the release. Put each test tag
  on its own commit.
- **G3. Two versions inside one build.** The updater compares against the
  `tauri.conf.json` version (the tag). Help → About, Copy Diagnostics and the
  "up to date" reply show `CARGO_PKG_VERSION` (`src-tauri/Cargo.toml`, 0.1.0),
  which `sync_version.sh` does not update. An rc build therefore says 0.1.0
  there, so use the build/describe line in About, which shows the tag. Fixing
  this is a product change (sync `Cargo.toml` too, or report
  `app.package_info().version`) and is not in this PR.
- **G4. The release workflow runs no tests.** It builds whatever commit is
  tagged. Tag only a commit whose CI run is green (for v0.1.0: the `main`
  merge commit after R4).
- **G5. A test release is public and Latest.** `prerelease: false` is needed,
  because `/releases/latest/` skips prereleases. Anyone who downloads the
  Latest dmg during the test gets the rc.

## R3. Cluster datasets on the real HPC

### In CI (fake ssh cluster: `desktop-macos` → Run cluster-dataset packaged-app E2E with a fake ssh)

| what | step |
| --- | --- |
| Test connection reports cluster datasets supported; detect finds OPV2V `test`, 3 scenes | CD-1 |
| Index with the detected split | CD-2 |
| The prepare preview is CPU-only, with the split and the camera-image mode | CD-3 (with #110: a 1-task array) |
| A wrong hash or no confirm submits nothing | CD-4 |
| A confirmed submit is exactly one sbatch; status follows it | CD-5, CD-6 |
| Prepare all (with #110: one sbatch, an array of one-CPU tasks, per-task claims) | CD-7 |
| Open serves the ready scenes over one ssh stream with no viewer job; images through the media root | CD-8 |
| Raw tree byte-identical; no secrets in requests or results | CD-9 |
| An older coperceive on the cluster gets an "update it with" message | CD-10 |
| Camera modes: previews from Settings, upgrading a scene, Remove previews | CD-11, CD-12, CD-13 |
| Two Opens → one viewer server, no Slurm job, one ssh stream | CD-14 |
| A viewer job that starts slowly is attached, not refused (Open Folder over HPC) | CD-15 |
| No nodes (sbatch fails): prepared scenes still viewable | CD-16 |

| Viewing while the prepare job runs | CD-18 |
| Scene navigation in the viewer: scene menu, ◀ ▶ and P/N, finished-scene offer, auto-continue | `test (3.x)` → `tests/test_viewer_browser.py::test_previous_and_next_scene_buttons_and_keys`, `::test_a_finished_scene_offers_the_next_one`, `::test_continue_to_the_next_scene_automatically`, `::test_the_app_switches_scene_in_place_through_the_hash` |
| SSH viewing reads only inside the dataset and matches local reads | `tests/test_remote_view.py` |

### Manual on the HPC (a real OPV2V or V2XSet split; DeepSeek's timing script, #111, records the prepare times)

Before you start, write down `date` and run `touch /tmp/raw-marker` on the
login node.

1. On the cluster's server profile, run Test connection.
   **Expected:** every row is green, including `cluster-datasets`. If the
   cluster's coperceive is too old, the row says "Update it with: …".
2. File → Open HPC Dataset… (or HPC workspace → the server → Datasets) → the
   split folder.
   **Expected:** a banner such as "OPV2V · test · N scenes", with the cache
   path shown.
3. Prepare whole dataset.
   **Expected:**
   - The preview script has `#SBATCH --array=0-<N-1>%8` and
     `--cpus-per-task=1`, and lists every scene in `SCENES=(…)`.
   - Changing "Scenes at once" to 4 shows "Updating preview…", then
     `%4` and a new hash.
   - Tick the confirmation and Submit: exactly one job.
   - `squeue -u $USER` shows `<job>_[…]` tasks and at most 4 running.
4. While it runs, watch the jobs indicator and the dataset view.
   **Expected:**
   - Scenes go Queued (job N) → Preparing → Ready.
   - The indicator reads "x ready · y preparing · z queued".
   - The first ready scene opens in the viewer by itself (Settings → "Open the
     viewer when the first scene is ready" is on).
   - You get a notice when the dataset finishes.
5. While prepare still runs, open another ready scene.
   **Expected:**
   - It opens in the same viewer window.
   - `squeue -u $USER` shows no new job (only the prepare array).
   - Playback is smooth, and "Buffering…" appears only briefly, if at all.
   - Scenes still preparing are not listed as viewable.
6. In the viewer, check scene navigation.
   **Expected:**
   - The scene menu lists every scene with its state.
   - ◀ ▶ and the P/N keys move between prepared scenes.
   - Choosing a scene that is not prepared offers "Prepare & open".
   - At the end of a scene, "View next scene (N)" is offered.
7. Check the camera modes.
   **Expected:**
   - Camera images show from the originals.
   - Settings → Cluster datasets → previews for this server makes the next
     prepare preview start with `--images previews` and a new hash.
   - Re-preparing one scene in previews mode shows the JPEG preview, and the
     full image on demand.
   - Remove previews (confirmed) returns that scene to the originals while it
     is open.
8. Settings → Cluster datasets → Viewing cache.
   **Expected:** the size in use grows after viewing, and Clear cache empties
   it. Viewing still works afterwards; it fetches the files again.
9. On the login node, run `find <raw root> -newer /tmp/raw-marker | head`.
   **Expected:** nothing; no file under the raw root changed.
10. Record:
    - the wall time from Submit to all ready (from #111 or the indicator);
    - `sacct -j <job> -o JobID,Elapsed,TotalCPU,MaxRSS`;
    - how long the first scene took to open.

    Do not call the prepare speed fixed until these numbers are in.

## R4. `feat/m2-import` → `main`

1. `gh pr checks 93`
   **Expected:** every check passes on the PR's current head. A pending check
   is not a pass.
2. Run:

   ```bash
   git fetch origin main feat/m2-import
   git merge-tree --write-tree origin/main origin/feat/m2-import; echo "exit=$?"
   ```

   **Expected:** `exit=0` and no `CONFLICT` lines; only the merged tree id is
   printed.
3. Merge #93 (Adarsh), wait for the `main` CI run to go green, then tag
   `v0.1.0` on that merge commit (Adarsh). The release then follows R2 steps
   2 and 6.
