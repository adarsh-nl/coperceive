# v0.1.1 release checklist

Every check below states what CI already proves (with the exact CI job, step, or
test) and what only a human can verify before, during, or after tagging. A
release needs every row green or explicitly waived by Adarsh. Agents never tag,
merge, edit, or publish a release; Adarsh does.

| id | check | what CI proves | what only a human can check |
| --- | --- | --- | --- |
| C1 | Per-OS install and first run (macOS arm64, macOS Intel, Windows, Linux) | Packaged build, bundled Python runtime, first-run library modal, welcome card, offline demo scene generation and viewer rendering on all 3 OSes (`desktop-macos`, `desktop-macos-intel`, `desktop-windows`, `desktop-linux`) | Gatekeeper right-click → Open on macOS; bare-metal Intel Mac hardware; interactive Windows SmartScreen ("More info → Run anyway") and NSIS wizard; interactive Linux desktop environment |
| C2 | Updater: `v0.1.0` updates itself to `v0.1.1` | Bundle version sync, 4-target `latest.json` generation, `minisign -Vm` verification of all 4 `.sig` files against `tauri.conf.json`, Linux `.deb` vs `.AppImage` rule, and UI banner/toast/bad-signature tests against a mock server | Real `v0.1.0` app downloading `v0.1.1` from `/releases/latest/download/latest.json`, verifying the signature, replacing itself on disk, and relaunching as `v0.1.1` |
| C3 | V2V4Real mirror / coordinate-convention check | Synthetic OpenCOOD V2V4Real-layout adapter tests (10 Hz clock, LiDAR-only optional cameras, `[roll, yaw, pitch]` in degrees, provisional `reflect_axis: y`, unverified convention warning, "seen by" hidden) | Visual inspection of one real extracted scenario from `/datasets/eemcs/ps/cv/opencood/v2v4real/test/` in the viewer to confirm whether traffic is right-hand-drive or mirrored |

## C2. Updater: `v0.1.0` updates itself to `v0.1.1`

### What CI already proves vs what requires the published release

| aspect | proved in CI? | where / why |
| --- | --- | --- |
| `sync_version.sh` sets `tauri.conf.json` version from the triggering `v*` tag (or `pyproject.toml` on untagged builds) and refuses ambiguous or non-semver tags | **Yes (CI)** | `tests/test_release_pipeline.py` |
| `write_latest_json.py --require-all` writes all 4 targets (`darwin-aarch64`, `darwin-x86_64`, `windows-x86_64`, `linux-x86_64`) with distinct URLs, non-empty signatures, and matching minisign `file:` trusted comments | **Yes (CI)** | `tests/test_write_latest_json.py`, `tests/test_release_pipeline.py`, and the `release.yml` dry run |
| All 4 updater archives (`Coperceive_aarch64.app.tar.gz`, `Coperceive_x64.app.tar.gz`, `Coperceive_0.1.1_x64-setup.exe`, `Coperceive_0.1.1_amd64.AppImage`) verify with `minisign -Vm` against `plugins.updater.pubkey` in `src-tauri/tauri.conf.json` | **Yes (CI)** | `.github/workflows/release.yml` (`publish-release` → `Install minisign and verify updater signatures`) |
| Sidebar update card ("New update available — coperceive X is ready"), "What's new" notes popover, "Later" dismissal, quiet 404 on launch, "You're up to date" toast on manual 404, and bad-signature rejection | **Yes (CI, mock server)** | `desktop-macos` (`scripts/desktop/e2e_mac.sh` Step 5d) and `tests/test_viewer_browser.py` using `window.__COPERCEIVE_UPDATE_URL__` |
| Installed `v0.1.0` binary polling `https://github.com/adarsh-nl/coperceive/releases/latest/download/latest.json`, downloading the real `v0.1.1` archive from GitHub Releases, verifying its signature with `tauri-plugin-updater`, replacing `/Applications/Coperceive.app` in place, and relaunching as `v0.1.1` | **No — requires the real published `v0.1.1` release** | The compiled `tauri-plugin-updater` inside the released `v0.1.0` app reads its endpoint from the compiled `tauri.conf.json` (`https://github.com/adarsh-nl/coperceive/releases/latest/download/latest.json`). That URL only serves `v0.1.1`'s `latest.json` once the `v0.1.1` GitHub Release is published and marked **Latest**. |

### Exact steps for testing the `v0.1.0` → `v0.1.1` update

#### Part A — Before tagging `v0.1.1` (prepare the `v0.1.0` baseline)

- [ ] 1. Install the released `v0.1.0` build (`Coperceive_0.1.0_aarch64.dmg` from
  `https://github.com/adarsh-nl/coperceive/releases/tag/v0.1.0`) into
  `/Applications/Coperceive.app` (right-click → Open the first time).
- [ ] 2. Launch `/Applications/Coperceive.app`.
  - Open **Coperceive → About Coperceive** (or **Help → About**) and confirm it
    shows **`v0.1.0`**.
  - Click **Help → Check for Updates…** while `v0.1.0` is still the Latest
    GitHub release.
  - **Expected:** Toast says **`You're up to date (0.1.0).`** and no sidebar
    update card is shown.
- [ ] 3. Quit `/Applications/Coperceive.app` and leave it installed in
  `/Applications` ready for Part B.

#### Part B — Immediately after tagging and publishing `v0.1.1` (requires the published release)

- [ ] 4. Once the `Release` workflow on tag `v0.1.1` finishes (`C5`), confirm in
  a terminal that GitHub's `latest` endpoint is live and serving `0.1.1`:
  ```bash
  curl -fsSL https://github.com/adarsh-nl/coperceive/releases/latest/download/latest.json | jq -r '.version, (.platforms | keys[])'
  ```
  **Expected:** Prints `0.1.1` followed by `darwin-aarch64`, `darwin-x86_64`,
  `linux-x86_64`, and `windows-x86_64`.
- [ ] 5. Launch the installed `v0.1.0` app (`/Applications/Coperceive.app`). If
  it was already running, click **Help → Check for Updates…**.
  **Expected:** The sidebar card above **Settings** appears:
  - Title: **`New update available`**
  - Version line: **`coperceive 0.1.1 is ready`**
  - Buttons: **`What's new`**, **`Install`**, and **`✕`** (`Later`).
- [ ] 6. Click **`What's new`** and confirm the popover opens for
  `coperceive 0.1.1`. Click **`✕`** (`Later`) and confirm the card hides for the
  session; then click **Help → Check for Updates…** and confirm the card comes
  back.
- [ ] 7. Click **`Install`**.
  **Expected:**
  - The card changes to **`Downloading update…`**.
  - `tauri-plugin-updater` downloads `Coperceive_aarch64.app.tar.gz` from the
    `v0.1.1` release, verifies `Coperceive_aarch64.app.tar.gz.sig` against
    public key `9AB294B56FC3C444`, replaces `/Applications/Coperceive.app` in
    place, and relaunches the app automatically.
- [ ] 8. After the app relaunches:
  - Open **About Coperceive** and **Help → Copy Diagnostics**: both must report
    **`0.1.1`**.
  - Click **Help → Check for Updates…**: toast must say **`You're up to date
    (0.1.1).`** and the sidebar update card must not appear.

### What to do if the update fails after tagging

If Step 5, 7, or 8 fails after `v0.1.1` is published:

1. **Stop offering `v0.1.1` immediately (rollback `Latest` to `v0.1.0`):**
   - On GitHub, open **Releases → `v0.1.0` → Edit**, tick **Set as the latest
     release**, and click **Update release** (or run
     `gh release edit v0.1.0 --latest`).
   - Because the app polls `/releases/latest/download/latest.json`, setting
     `v0.1.0` back as Latest immediately serves `v0.1.0`'s `latest.json`
     (`"version": "0.1.0"`), so no other `v0.1.0` installation is offered the
     broken update.
   - **Never delete the `v0.1.0` release.** If no release is marked Latest, the
     endpoint returns HTTP 404, which the app treats as "up to date".
2. **If the failure was only in release assets or `latest.json`:**
   - Check the error shown in the sidebar card (`Retry` / signature / network
     message) and inspect `latest.json` on the `v0.1.1` release. Note that `v0.1.0`
      expects the `darwin-aarch64` entry in `latest.json` to have a valid
     minisign signature matching `plugins.updater.pubkey`.
3. **If the failure is a bug in the `v0.1.1` binary itself:**
   - Any installation that already updated to `v0.1.1` will stay on `v0.1.1`
     because the Tauri updater never downgrades (`0.1.1` → `0.1.0`).
   - Fix the issue on `main`, verify with a `release.yml` dry run, and tag and
     publish **`v0.1.2`**. Both `v0.1.0` and `v0.1.1` installations will then
     update cleanly to `v0.1.2`.

## C3. V2V4Real mirror / coordinate-convention check

### What CI already proves

- `tests/test_adapters_v2v4real.py` verifies `coperceive/adapters/builtin/v2v4real.yaml`
  on synthetic OpenCOOD V2V4Real-layout fixtures:
  - 10 Hz frame clock (`scale_us: 100000`, 0.1 s step per the CVPR 2023 paper);
  - optional camera sensor records (`records: {prefix: camera, optional: true}`)
    so the LiDAR-only release validates and plays with no camera sensors;
  - box angles `[roll, yaw, pitch]` in degrees;
  - provisional `source_handedness: left`, `reflect_axis: y` (`world_frame:
    v2v4real-world`) and the unverified coordinate-convention warning;
  - viewer hides "seen by" colouring for V2V4Real (`web/src/desktop/` / viewer
    style tests) because per-CAV `vehicles` keys are not shared track IDs.

### What only a human can check on the HPC

- [ ] On the cluster where `/datasets/eemcs/ps/cv/opencood/v2v4real/test/` is
  extracted (9 scenarios, LiDAR-only, `docs/datasets/v2v4real.md`):
  1. Index and prepare one scenario (for example
     `testoutput_CAV_data_2022-03-15-09-54-40_0`) and open it in the viewer.
  2. Check whether the vehicles drive on the **right-hand side of the road**
     (Columbus, Ohio real-world driving) and turns/intersections match natural
     right-hand traffic, or whether the scene is left-right mirrored.
  3. Confirm that the unverified coordinate-convention warning is shown in the
     UI/docs. (If the scene is mirrored, remove `reflect_axis: y` in
     `coperceive/adapters/builtin/v2v4real.yaml` in `v0.1.2`; if it is not
     mirrored, remove the provisional warning in `v0.1.2`.)
