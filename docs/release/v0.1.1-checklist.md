# v0.1.1 release checklist

Every check below states what CI already proves (with the exact CI job, step, or
test) and what only a human can verify before, during, or after tagging. A
release needs every row green or explicitly waived by Adarsh. Agents never tag,
merge, edit, or publish a release; Adarsh does.

### What to do if the update fails after tagging

If Step 5, 7, or 8 fails after `v0.1.1` is published:

1. **Stop offering `v0.1.1` immediately (rollback `Latest` to `v0.1.0`):**
   - On GitHub, open **Releases → `v0.1.0` → Edit**, tick **Set as the latest
     release**, and click **Update release** (or run
     `gh release edit v0.1.0 --latest`).
   - Because the app polls `/releases/latest/download/latest.json`, setting
     `v0.1.0` back as Latest immediately serves `v0.1.0`'s `latest.json`
     (`"version": "0.1.0"`), so no other `v0.1.0` installation is offered the
     broken update.
   - **Never delete the `v0.1.0` release.** GitHub's `/releases/latest` redirect
     automatically falls back to the most recent non-draft, non-prerelease
     release (it does not return 404 as long as any non-draft, non-prerelease
     release exists); keeping `v0.1.0` published and explicitly marked Latest
     (or marking `v0.1.1` as pre-release) ensures `/releases/latest` resolves to
     `v0.1.0` instead of `v0.1.1`.
2. **If the failure was only in release assets or `latest.json`:**
   - Check the error shown in the sidebar card (`Retry` / signature / network
     message) and inspect `latest.json` on the `v0.1.1` release. Note that `v0.1.0`
     expects the `darwin-aarch64` entry in `latest.json` to have a valid
     minisign signature matching `plugins.updater.pubkey`.
3. **If the failure is a bug in the `v0.1.1` binary itself:**
   - Any installation that already updated to `v0.1.1` will stay on `v0.1.1`
     because the Tauri updater never downgrades (`0.1.1` → `0.1.0`).
   - Fix the issue on `main`, verify with a `release.yml` dry run, and tag and
     publish **`v0.1.2`**. Both `v0.1.0` and `v0.1.1` installations will then
     update cleanly to `v0.1.2`.

## C3. V2V4Real mirror / coordinate-convention check

### What CI already proves

- `tests/test_adapters_v2v4real.py` verifies `coperceive/adapters/builtin/v2v4real.yaml`
  on synthetic OpenCOOD V2V4Real-layout fixtures:
  - 10 Hz frame clock (`scale_us: 100000`, 0.1 s step per the CVPR 2023 paper);
  - optional camera sensor records (`records: {prefix: camera, optional: true}`)
    so the LiDAR-only release validates and plays with no camera sensors;
  - box angles `[roll, yaw, pitch]` in degrees;
  - provisional `source_handedness: left`, `reflect_axis: y` (`world_frame:
    v2v4real-world`) and the unverified coordinate-convention warning;
  - viewer hides "seen by" colouring for V2V4Real (`web/src/viewerStyle.test.ts`)
    because per-CAV `vehicles` keys are not shared track IDs.

### What only a human can check on the HPC

- [ ] On the cluster where `/datasets/eemcs/ps/cv/opencood/v2v4real/test/` is
  extracted (9 scenarios, LiDAR-only, `docs/datasets/v2v4real.md`):
  1. Index and prepare one scenario (for example
     `testoutput_CAV_data_2022-03-15-09-54-40_0`) and open it in the viewer.
  2. Check whether the vehicles drive on the **right-hand side of the road**
     (Columbus, Ohio real-world driving) and turns/intersections match natural
     right-hand traffic, or whether the scene is left-right mirrored.
  3. Confirm that the unverified coordinate-convention warning is shown in the

     `coperceive/adapters/builtin/v2v4real.yaml` in `v0.1.2`; if it is not
     mirrored, remove the provisional warning in `v0.1.2`.)

  (run in `ci.yml` job `landing`) verify that:
  - each platform gets its right primary installer from the `v0.1.1` asset names
    (`mac-arm64-dmg`, `mac-x64-dmg`, `windows-setup` with SmartScreen note,
    `linux-appimage` + `linux-deb`), and Safari on macOS (which hides the CPU
    architecture) offers both Apple Silicon and Intel DMGs;
  - when a live GitHub release tag (`v0.1.1`) differs from the release baked in
    at site build time (`v0.1.0`), the live `v0.1.1` release replaces it
    immediately in the browser.
- `tests/test_landing_page.py` (run in `ci.yml` job `landing`) runs Playwright
  and axe-core WCAG 2.1 AA checks against the built site.
