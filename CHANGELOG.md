## [Unreleased]

### Security
- Remote viewer: the session file is written as data (SCRIPTS-01, security review #170). The cluster job wrote its session file with an unquoted shell heredoc, so a data-root folder name could set the session's `ip` and `port`, and the login node then sent the session bearer token to that address. The job now writes the file with `json.dump` from separate arguments, 0600, through a temporary file. Session ids must be plain names (no `..`, `/` or spaces), and data roots, media roots, the viewer page folder and the interpreter path may not contain control characters. `start` and `status` use a session file only when its job id and session id match the job just submitted. **Behaviour that changes:** `coperceive remote start --uuid` refuses ids that are not 1–128 of `A-Za-z0-9._-`; the app never passes one.
- **OpenCOOD checkpoints no longer run code from the archive by default.** The plugin used to parse a checkpoint archive's `config.yaml` with OpenCOOD's own `load_yaml`, which uses PyYAML's full loader and runs `eval(yaml_parser)`. So a crafted archive ran code even with `trust_checkpoint_pickle=false`. The plugin now reads the config itself with a safe loader that still accepts genuine training configs: OpenCOOD's float resolver (`1e-3`), plus `!!python/tuple` and the numpy scalar/dtype/array tags that `yaml.dump` writes, rebuilt as data. It applies `yaml_parser` only as a `load_<name>_params` name looked up in the installed OpenCOOD. Any other `!!python/` tag or `yaml_parser` expression is refused with an error naming `--option trust_checkpoint_pickle=true`, and that option now also lets OpenCOOD's own loader parse such a config. Separately, `torch.load(weights_only=True)` is no longer trusted on torch older than 2.6.0 (CVE-2025-32434). On torch 2.5.1 or older, on a 2.6.0 pre-release, or when the torch version cannot be read, loading weights now needs `trust_checkpoint_pickle=true` or a torch upgrade; on torch 2.6.0 and newer nothing changes. The `loaded:` line in `plugin.log` now records `config_loader=safe` or `config_loader=opencood load_yaml (trusted)`.
- `coperceive serve`: with `--root-path` set, the bearer-token and `X-Coperceive-Request` checks never ran, because uvicorn puts the prefix in front of the path, so every `/api` route behind a proxy was open. They now apply to every `/api` route whatever the root path. Without a token, serve now answers only `127.0.0.1`, `localhost` or `[::1]` on its own port, which stops DNS-rebinding pages. Any other Host, another port included, now gets 400, so an SSH tunnel must keep the same local port, and token-less serve behind a hub proxy no longer works: use `COPERCEIVE_TOKEN` or `--token-file` and enter the token in the page. `--token-file` must now be a non-empty regular file owned by you, not a symbolic link, with mode 0600 or 0400. An empty file is now an error; before, the server quietly ran without a token. A `jobs.sqlite` (or its `-journal`, `-wal` or `-shm`) that is a symbolic link is now refused with a 400 instead of creating a database at the link's target. The Rerun export file name now comes from the scene id only when that id is plain (letters, digits, `_`, `-`); otherwise it uses the folder name or `scene`, so a manifest can no longer write the `.rrd` into another folder.
- Server profiles now refuse a results folder or code folder that contains `$`, a backtick, a double quote, a backslash, a line break or another control character, and a results folder that starts with `~` (type the absolute path, for example /home/<you>/results). Job scripts wrote the results folder into `OUT_DIR="..."` and into `#SBATCH --output/--error` lines, so a shared lab profile (or a typed path) could run commands on the compute node. The check runs on save, on lab-profile import, and again before the full-run or dataset-preparation script is rendered. A saved plan whose output folder contains these characters is also refused. SSH now always gets `--` before the destination, and an SSH alias, host name or user name that starts with `-` is refused, so ssh can no longer read it as an option such as `-oProxyCommand=`. Code folders with spaces, and `~/` code folders, work as before; results folders with spaces are now refused (see below). A saved profile whose results folder starts with `~` (which never worked for runs) must be edited to an absolute path before its next run.
- CLI Slurm job scripts and archive readers refuse unsafe values (security review, group cli-scripts). `coperceive model run --slurm` and `robustness sweep --slurm` used to accept values that could add commands to the job script or make its EXIT trap delete a parent directory:
  - **Scratch template:** may now name only $USER, $SLURM_JOB_ID or their ${...} forms. A '..' segment, '~', any other variable, or a trailing newline is refused. ${SLURM_JOB_ID} is now accepted.
  - **Manifest values:** the manifest name, model keys and option names may not end in a newline. resources.slurm_constraint must be a Slurm feature expression (letters, digits, _ . , : - joined by & | * [ ] ( )). environment.secrets entries must be environment variable names.
  - **Run ids:** a sweep --run-id with --slurm must be letters, digits, '.', '_' or '-', as for `model run`. Run ids in general may no longer contain line breaks or other control characters.
  - **Checkpoint and interpreter:** a checkpoint file name with a backslash or control character, and a --slurm-python path with a line break, are refused with a plain error.
  - **Bundle check:** scripts/check_bundle_assets.py unpacks a .deb with tarfile's "data" filter, so a '..' member or an escaping link fails the check instead of writing outside its temporary directory.
  - **maps fetch:** reads each .xodr member in 1 MiB chunks and refuses one over 20 MiB (exit 2 with the member name). An earlier good file is kept.

  Valid profiles, manifests (Griffin's "a40" and "a40|a100" included), run ids and packages give the same scripts and files as before.
- A server profile's results folder may no longer contain spaces, '#' or quotes. Slurm reads the results folder from the job script's `#SBATCH --output` and `--error` lines. It splits those lines at spaces and cuts them at '#', so a shared lab profile with a results folder such as `/dev/null --export=ALL,BASH_ENV=/path/evil.sh #` could add Slurm options to every job and run code under your cluster account. Such folders are now refused on save, on lab-profile import, and before the run or dataset-preparation script is rendered, with a message that explains why. Rename or choose a folder without spaces, '#' or quotes. The dataset-preparation script also refuses a job name, partition or time limit that contains spaces, '#' or quotes. Code folders with spaces still work.
- More manifest values are checked before they reach a Slurm job script, and `maps fetch` is protected against oversized tar headers (security review round 2, group cli-scripts).
  - **Manifest:** `outputs.artifacts` names (and therefore `transient_artifacts` and `depends_on[].artifact`) must be `[A-Za-z0-9_.-]+` and not `.` or `..`. `environment.modules` entries must be `[A-Za-z0-9_.+/@:-]+` with no `.` or `..` segment. Before, a transient artefact name was written raw inside `rsync --exclude='...'`.
  - **Job script:** `model run --slurm` checks every model key, module, transient artefact, dependency and checkpoint option name again before writing the script, so a Manifest built in code cannot skip the rules.
  - **maps fetch:** a GNU long-name or pax header payload over 64 KiB is refused, as are more than 8 header extensions before one member and any GNU sparse member. The command exits 2 with a message. Member headers are no longer all kept in memory, so a doctored package can no longer push fetch to gigabytes of memory; reading a huge package can still take a long time.
  - The Griffin, OpenCOOD and fixture manifests and official-shaped packages behave as before.
- **OpenCOOD torch version gate follows PEP 440.** Post-releases of torch 2.6.0 such as `2.6.0.post1` or `2.6.0.post100+cpu` are no longer refused as older than 2.6.0. Pre-releases and dev builds of 2.6.0 still need `trust_checkpoint_pickle=true`, as do versions that are not PEP 440. The `trust_checkpoint_pickle` description in the manifest and the plugin README now says what the option covers: it lets OpenCOOD's own `load_yaml` read a `config.yaml` that the safe reader refuses, and it is required for any weights load on torch older than 2.6.0.
- `coperceive serve`: `jobs.sqlite` is now opened so the file checked is the file SQLite uses. The folder is opened once, and a new database is created with `O_EXCL|O_NOFOLLOW`. SQLite opens it in `mode=rw`, so it never creates a file itself. Before anything is written, the resolved name, device and inode are verified again; a link swapped in while the server runs is refused with 400 and nothing is created or written outside the folder. A `jobs.sqlite` (or `-journal`/`-wal`/`-shm`) that is a hard link, a FIFO or a directory is now refused with 400. Before, a FIFO journal hung the request and a hard link wrote into the other file. Note: a hard-linked `jobs.sqlite`, e.g. from `rsync --link-dest`, must now be copied or removed.
- **Result bundles never follow a link (FOLD-03).** `coperceive bundle export`/`preview` and the app's Export bundle walk every scene and run folder they read without following links, and `lstat` each entry first. A symbolic link (to a file, a folder, another link, or a file in the same scene), a FIFO or another non-regular file now refuses the whole export with an error that names it; before, a link in a shared scene folder put its target (for example a key or a credentials file) into the shareable `.cpbundle`. Staged files are checked the same way before scrubbing, copies open their source with `O_NOFOLLOW`, the archive holds exactly the files `bundle.json` lists, and a recorded camera image that is missing refuses the export instead of being skipped. A hard link is refused too, and each file is read only after a check that it is still the file the walk saw, so a file or folder swapped in after the walk is refused. Only the exported scenes are walked. Opening refuses members named `open.json` or `BUNDLE.JSON` (ARC-2), counts every non-table member under `scenes/` against the sensor cap whatever its name, refuses such members in a bundle that says its sensor data is omitted, and re-checks a bundle opened before. **Behaviour that changes:** a scene folder with a link inside it cannot be exported until the link is replaced by a copy. The one exception is a prepared cluster scene's `raw` camera link: without sensor data it is left out (never followed) and listed in `bundle.json` under `omitted_links` by its path, never its target; with sensor data it is refused. In every JSON file a bundle stages, the value under a credential-like key (`password`, `secret`, `token`, `api_key`, `access_key`, `private_key`, `authorization` and close variants, also as a suffix such as `hf_token` or `X-Api-Key`) is now replaced with `"<redacted>"`. A served bundle's private jobs-database folder is removed at shutdown, and stale ones later.
### Added
- Result bundles open in the viewer, read-only (PR #160 takeover): **Open bundle…** shows the bundle's frames, ground truth, predictions and scores with a banner that says whether sensor data is included (Coperceive demo scenes only: the scene's `COMPLETE.json` must record `generator: "coperceive demo"` and the `generic` adapter, the exporter must tick "Include sensor data", and the frames must fit the 50 MiB cap, checked before writing and again before extracting), comes from your own local copy of the same scene in your library (read in place, never copied; it must resolve inside the library root), or is left out with the reason. Third-party datasets, Griffin included (its catalog entry requires accepting terms), never travel. `coperceive serve --root <bundle>/scenes --predictions <bundle>/predictions --bundle-info <bundle>/open.json` serves the same view; every route keeps the token, CSRF and loopback-Host checks.
- `protocol: default | legacy` in the eval config and `eval run --protocol`: one switch for the v0.1.1 evaluation rules (PR #165; [Evaluate](docs/eval.md), "Reproduce v0.1.1 numbers").
- Evaluator verification (ADR 0016, PR #165). `docs/eval-spec.md` states what `eval run` and `eval report` compute, how that compares with the benchmarks' own definitions (every claim cited or marked unverified), where it differs, and 37 golden cases worked by hand. `tests/reference_eval/` is a second evaluator written from that page alone: it imports nothing from `coperceive` and takes its footprint overlap from an exact polygon overlay (shapely). The `test` job now runs it against the product on seeded random scenes (headings at ±π, heavy overlap, duplicate and equal-score predictions, empty samples, boxes on the range limit, tiny and huge boxes, worlds far from the origin), checks the invariants a metric must keep, and reads the golden table. `shapely` and `types-shapely` join the `dev` extra only; the runtime dependencies are unchanged.
- Concurrent, cancellable cluster-dataset streaming (streaming steps 1–2, backend, PR #150): the remote-view streamer answers requests on a bounded pool for protocol-2 clients (protocol-1 clients keep the old serialized, in-order replies so a large point-sweep read no longer holds up small manifest/stat replies for them), protocol 2 adds per-request `queue_ms`/`read_ms`/`bytes` timings, and a `cancel` op (queued reads are skipped; an in-flight read's reply is dropped). The viewer server exposes bounded, versioned timings at `GET /api/stream-stats` and cancels a remote point-cloud read when the browser disconnects. New `scripts/bench/stream_bench.py` measures playback, per-request timings, head-of-line blocking and seek-cancellation over a synthetic scene and fake link (`--smoke` runs in CI).
- Time-based streaming buffer for the viewer (streaming steps 1–2, viewer, PR #150): Settings → Viewer chooses 1/3/5 s of buffered playback (default 3 s) and a 256/512/1024 MB client buffer (default 512 MB); the fixed four-frame horizon is replaced by a priority scheduler (current frame, its boxes, then prefetched sweeps), a byte-bounded cache evicts behind the playhead first, the timeline shows a buffer bar, playback pauses with "Buffering…" instead of stuttering and resumes at ≥1 s buffered, and an optional stats line shows buffer-ahead, MB/s and frame-load p50/p95.

### Changed
- **v0.1.2 gives other AP numbers than v0.1.1 for the same predictions** (PR #165).
  - **Why:** the default protocol is now the OPV2V and V2X-ViT one. AP ranks predictions frame by frame (`ranking_scope: per_frame`), and a `fused` output is scored against the boxes of every agent within 70 m that a connected agent's LiDAR hits (`gt_scope: connected_union`, `comm_range_m: 70`). Both entries below give the sources. That OpenCOOD's local sort is one frame is **unverified**, so the `per_frame` default rests on an unverified reading (`docs/eval-spec.md` A.5).
  - **What changes:** every AP, mAP and per-class AP, and the ground truth of `fused` outputs. Counts, precision and recall change where a `fused` output gains ground truth. Several defects are fixed as well (entries below); some of those fixes change numbers, counts included, under either protocol.
  - **How to get the old numbers:** `protocol: legacy` in the eval config, or `coperceive eval run <run_id> --root <scenes> --protocol legacy`. It sets `ranking_scope: pooled` and `gt_scope: ego_only`. On the demo run, every count, precision, recall and AP then equals v0.1.1's on the same Python version (a class mean can differ in the last bit between Python 3.11 and 3.12+, in v0.1.1 too); `tests/test_eval_legacy_protocol.py` checks this against values written by the v0.1.1 code. The switch does not bring back the fixed defects: the bottom `all` row, the APs of `eval compare --by`, and the BEV IoU in its last bits still differ ([Evaluate](docs/eval.md), "Reproduce v0.1.1 numbers").
  - **Labels:** a report under `protocol: legacy` is headed `protocol: legacy (pooled, ego-only)`, as one evaluated by v0.1.1 is, and `eval compare` sets the two side by side.
- AP ranks predictions frame by frame by default (`ranking_scope: per_frame`, PR #165).
  - **Why:** OpenCOOD's documentation says its default evaluation, which the OPV2V paper reports, does not sort detection scores over the whole test set; a global sort is an opt-in flag ([OpenCOOD README](https://github.com/DerrickXuNu/OpenCOOD), "Test the model"; [PR #105](https://github.com/DerrickXuNu/OpenCOOD/pull/105); [issue #101](https://github.com/DerrickXuNu/OpenCOOD/issues/101)). That the local sort is one frame, with one curve over the test set, is the behaviour of OpenCOOD at commit `31ba160` as read by a separate session that wrote it down in prose, with no code copied (ADR 0016 two-room; `docs/eval-spec.md` A.5). The AP then depends on the order of the frames, in OpenCOOD and here (`docs/eval.md`).
  - **What changed:** the AP walk now takes a scene's predictions frame by frame, earliest first, and by score within a frame. Scenes are joined with no sort over the whole list.
  - **Old rule:** `ranking_scope: pooled` keeps the single sort over everything, as KITTI does.
  - **Records:** every `metrics.json` records `ranking_scope`. One without it is reported as "legacy (pooled, ego-only)".
  - **Numbers that change:** every AP, mAP and per-class AP of `eval run`, `eval report`, `eval compare`, `eval compare --by` and the paper export. Counts, precision and recall do not change.

- The bottom `all` row of `eval report` and `eval compare` no longer depends on the order of the rows in `boxes.parquet` (PR #165).
  - **What was wrong:** under `per_frame`, the row over every output joined each scene's outputs in the order they first appear in the file, so the same predictions written in another order could give another AP. For example, a true positive at 0.5 for one agent and a false positive at 0.9 for another gave 0.5 or 0.25.
  - **Now:** the records of every output are merged into one documented order (`docs/eval-spec.md` A.8). Under `per_frame`: scene, time, score (highest first), `agent_id`, `source`, then row order. Under `pooled`: score first, then the same keys. For one output this is the order it already had.
  - **Numbers that change:** the AP, mAP and per-class AP of the bottom `all` row only, under either ranking scope, when outputs of one frame interleave by score. Per-scene rows and per-output `all` rows do not change, and neither does the robustness sweep's cell mAP when a run has one output.
  - **On the demo run** (bottom `all` row, AP@0.5 / AP@0.7, before → after): mAP 0.537 → 0.540 / 0.281 → 0.281; car 0.997 → 0.997 / 0.712 → 0.711; cyclist 0.484 → 0.498 / 0.112 → 0.113; pedestrian 0.129 → 0.125 / 0.018 → 0.018.
- A `fused` output is scored against the ground truth of every connected agent (`gt_scope: connected_union`, PR #165).
  - **Why:** OPV2V's evaluation targets are the vehicles hit by at least one LiDAR point from any connected vehicle, and it ignores vehicles outside the 70 m broadcast range ([OPV2V paper](https://arxiv.org/abs/2109.07644), Sec. V-B). V2X-ViT states the same rule ([V2X-ViT paper](https://arxiv.org/abs/2203.10638), Sec. 4.2). That the targets are the union of the connected agents' own annotations is our reading of those sentences, and that V2XSet's per-agent files list only boxes the agent's LiDAR hits is not documented: both **unverified** (`docs/eval-spec.md` A.4).
  - **What changed:** at each time, a `fused` output's ground truth starts with the ego's own boxes. Each agent within `comm_range_m` (70 m, horizontal) then adds the boxes that hold at least one LiDAR return from the ego or a connected agent. A box that the spec's A.9 pairing matches to one already in the set is not added again. When there is no sweep at that time, every connected agent's list counts as observed.
  - **Unchanged:** `single` and every other output keep their own agent's boxes.
  - **Cooperative counts:** `recovered` and `only_other_agent` now also count objects that only a connected agent annotated.
  - **Old rule:** `gt_scope: ego_only` keeps it.
  - **Records:** `matches.parquet` gains `gt_agent_id`, the agent that annotated each ground-truth row.
  - **Our choices (unverified):** the range is horizontal; the ego's boxes are kept without a point test; a box two agents annotated counts once. All are listed in `docs/eval-spec.md` A.4.
  - **Numbers that change:** for `fused` outputs only: `gt`, `tp`, `fp`, `miss`, precision, recall, every AP, `recovered`, `only_other_agent` and `recovery_rate`. Outputs of any other source are unchanged.
  - **On the demo run:** no change; it has no `fused` output (its one source is `noisy`).
- AP is labelled as a bird's-eye-view AP, and every report names its protocol (PR #165).
  - **Labels:** `eval report`, `eval compare`, its `--by` breakdowns and the paper export say `mAP@0.5 (BEV)` and `AP@0.5 (BEV)`. Under `criterion: centre` they say `AP@<t> m (centre)`.
  - **Protocol line:** `eval report` and `eval compare` open with a `protocol:` line.
  - **Files:** `metrics.json` carries `"iou": "bev"`. `compare.json` carries a `protocol` object (optional in its schema). The paper export names the protocol in each table caption.
  - **Refusal:** `eval compare` refuses two runs scored under a different ranking scope, ground-truth scope or communication range, or a legacy run beside a current one.
  - **Not yet labelled:** the app's scores view. That file is the viewer's, and the change is routed.
  - **Numbers that change:** none. Column names and the first line of the report text change, so scripts that read `eval report` columns by name need the new names.
  - **On the demo run:** no number changes.

### Fixed
- The synthetic demo scene's LiDAR is written in the recording agent's body frame (GEN-6): it used to store world points where the app reads sensor-frame samples, so the viewer applied the agent pose twice and every cloud was about 25 m off (`cav-b`'s also turned 90°). The junction is also dressed for the product tour: denser LiDAR (681 points per sweep median, up from 306), buildings, trees, parked cars and richer camera renders, all still generated at runtime and deterministic. Measured for seed 0: the full demo tree is 12,986,276 bytes (12.4 MiB / 13.0 MB; the `scenes/demo-junction` folder the Library shows is 4,202,815 bytes) and generation takes 11.8 s warm on Apple Silicon, 24.7 s on a first cold run and 7.9 s on the CI runner. The welcome card's approximate demo cache size is now "about 12.4 MiB" instead of "about 8 MiB".
- The HPC workspace waits less for a dataset index: the last scene list for a server/adapter/raw root/split is shown at once, labelled cached, while the same read-only index command re-checks the raw tree in the background ("checking for changes…"). The cache is keyed by those four values and persists across restarts; every open still runs one index on the login node (about 45–60 s on OPV2V train on the real cluster), it just no longer blocks the view. (App-state part of the V2V4Real 0-scene report; the cluster-side root cause is unverified.)
- The Servers sidebar lists every recognised split of an open dataset, not only the one opened; clicking another split opens it from detect's own per-split adapter and scene count, without a second folder check.
- The Servers browser only opens a dataset after the selected folder's own check completes, so a leftover or in-flight "Checking what this folder holds…" result cannot open a dataset; the "Checking what this folder holds…" line no longer stays forever when the check is skipped or finds nothing. An index that returns no scenes now names the per-scene errors or the detect/index disagreement and offers a retry instead of a bare "No scenes in this split", and a change check that is cut short says it could not confirm the list rather than claiming it changed. The reported V2V4Real "detect 9 / index 0" state is **not reproduced end to end**: a V2V4Real-shaped fixture gives 9 scenes from detect and 9 from index, so the cluster-side reason the real scenes were unreadable is UNVERIFIED; the view now diagnoses the disagreement when it happens.
- BEV IoU no longer depends on where the scene sits in the world (PR #165). The footprints were clipped and their areas summed in absolute world coordinates, so precision fell with distance from the world origin. Against an exact polygon overlay, on 20,000 pairs of boxes 0.5 to 8 m long per offset, the old IoU was off by at most 1e-13 within 30 m of the origin, 2e-10 at 1 km, 4e-5 at 300 km, 8e-4 at (400 km, 4000 km) and 4e-2 at 10,000 km, and a centimetre-sized box that far out could score IoU 0 against itself. Both footprints are now taken about the midpoint of the pair; the error is under 3e-15 at every offset. **Numbers that change:** `iou_bev` of every pair in the last bits, and, only for scenes with world coordinates of hundreds of kilometres, any `tp`/`fp`/`miss`, precision, recall and AP that rested on a pair within that error of a threshold. **On the demo run:** no status, count, precision, recall or AP changes and `eval report` prints the same text; the largest change in `metrics.json` is 2.2e-16, in `tp_errors.iou_bev.mean`. Whether any dataset converted today has coordinates that large is unverified.
- `eval report` and `eval compare` count a recovered box once in the bottom `all` row (PR #165). `recovered` and `lost_by_fusion` compare an agent's `single` and `fused` outputs box by box and are stored on both; the row over every output summed them once per output, so it showed twice the number of boxes (three times with a third source). They are now taken once per scene and agent. **Numbers that change:** those two columns of the last `all` row, and their deltas in `eval compare`. The per-output `all` rows, every per-scene row and `metrics.json` are unchanged. **On the demo run:** no change; its only source is `noisy`, so both counts are 0.
- `eval report`, `eval compare` and the robustness sweep refuse a run whose scenes were evaluated with different configs (PR #165). `eval run --scenes ... --config ...` can re-evaluate part of a run; the headline then pooled statuses judged under two rule sets (another range, criterion, class map or threshold list) into one `mAP@<t>`, with exit code 0. The commands now stop with the two scene ids and say to run `eval run` again over every scene with one config. **Numbers that change:** none for a run evaluated with one config. **On the demo run:** no change.
- Scenes and agents a model found nothing in no longer drop out of the counts (PR #165). A run now covers every scene it has a prediction file for, even an empty one, and `coperceive model run` and `predictions import --scene` write that file when the model returned no box. Every output of the run is evaluated in every covered scene where its agent exists, so missed ground truth always counts. Before, a scene with no detection had no prediction file and was skipped, and an agent with no row in a scene had no output there: its ground truth was left out of `gt`, `miss`, recall and AP. Recall and AP were therefore too high, always in the model's favour. **Numbers that change:** `gt`, `miss`, recall, per-class AP and mAP of every headline row, for any run with a scene or an agent the model found nothing in. **On the demo run:** no change. Its only outputs are `cav-a` and `cav-b`, and both have rows in its one scene. (`rsu` never has a prediction, so it is not an output of the run.)
- Per-bin AP of `eval compare --by` is the AP of the bin, and stays within [0, 1] (PR #165). The definition is now written in `docs/eval-spec.md` A.11. Nothing is matched again: ground truth outside the bin is treated as ignored, as COCO, PASCAL VOC and KITTI treat objects they do not evaluate. A true positive therefore counts in the bin of the box it was paired with, and is neither a true nor a false positive anywhere else. A false positive counts in the bin of its own distance, class or scene, and in every occlusion and agent-count bin. Before, a prediction followed its ground truth only through the operating-point pair. A true positive scored under `score_threshold` landed in a bin of its own, so a distance bin could report AP 2.0, and occlusion and agent-count bins held no false positive at all, which made them a recall. `matches.parquet` gains one `gt_row_at_<i>` column per threshold (the paired box in that AP pass) and `outcomes.json` a `gt_row_at` field. An evaluation written before this is refused by `eval compare --by` with a message to run `eval run` again. **Numbers that change:** every AP of `eval compare --by` and `compare.json`, and the paper export's breakdown tables. **On the demo run** (AP@0.5 and AP@0.7, before → after): cav-a, objects seen by 2 agents: 0.659 → 0.516 and 0.315 → 0.282; cav-b, same bin: 0.695 → 0.567 and 0.304 → 0.282. Every demo object is seen by two agents, so these bins now equal the output's overall AP. Distance bins are unchanged, and the demo has no visibility values, so it has no occlusion bins. The empty `unknown` agent-count bin, which existed only to hold unpaired predictions, is gone.
- `eval compare` says when its runs were evaluated with different configs (PR #165). It only checked that the threshold lists were equal; two runs scored with another range, score threshold, class map or criterion were put side by side and the `b − a` columns carried the config difference with nothing to show it. A `note:` line above the tables now names each key that differs with both values. The comparison is still printed. **Numbers that change:** none. **On the demo run:** no change.
- A class named `mean` or `mean_model` is refused by `eval run` (PR #165). The `ap` table of `metrics.json` holds one entry per class beside those two keys, so a class with one of those names had its AP overwritten by the mean and was then averaged into `mean_model` as that mean. The scene now fails with a message that names the class. **Numbers that change:** none for any other class name. **On the demo run:** no change.
- An evaluation config with `criterion: centre` and no `thresholds` is refused (PR #165). It used to take the default `[0.5, 0.7]`, which are IoU values: the run was scored at a centre distance of 0.5 m and 0.7 m, an increasing list the centre rule itself forbids, and the report still read `mAP@0.5` and `mAP@0.7`. **Numbers that change:** none for a config that names its thresholds. **On the demo run:** no change.

Camera image planes follow their agent. With camera images shown in the 3D view, a camera's image plane was posed only after its image loaded, and every frame change cancelled the pending load. Over the SSH link, where an image takes longer than the 100 ms sample gap, the plane stayed at an earlier sample's pose while the ego, boxes and frustum lines moved on. The remote viewer page is no longer uploaded again when two sessions start at the same moment. Each start fetched the remote cache's manifest into a temporary file named from the process id and the clock, and macOS clocks tick in whole microseconds, so two starts could share one file: one deleted the other's fetched manifest, which then looked like a missing cache. Temporary names now carry a per-process counter. This also made `remote_static::tests::uploads_once_then_skips_a_complete_cache` fail now and then, because the cache tests run in parallel in one process.

Prepare reads raw files the way the cluster's shared filesystem needs. Real timing (job 670409, one V2XSet scene) showed cold reads at ~150 ms per file (6.4 files/s; 800 MiB/s warm): ~11 min of waiting against ~2 min of CPU, which the old sequential reader paid file by file. Each prepare task now reads its records and sweeps 16 at a time ahead of the parser (`COPERCEIVE_IO_THREADS`, set in the script), in the order the build consumes them; camera previews are read and encoded 16 at a time; each per-frame record is parsed once instead of twice (poses and boxes); "Read originals" opens no PNG (verified). The YAML loader warns when libyaml is missing. Every scene writes a timing line (read wait, build, write, previews, CPU, files, YAML loader) to the job log and to `<cache>/.timing.jsonl`; the prepare preview shows an estimated wall time from the scenes' raw file count, or from the last run's timing log when there is one, and says the shared filesystem is the limit. The default "Scenes at once" is a filesystem budget (8 tasks × 16 reads). With a simulated 150 ms per cold file, a synthetic scene went from 32.6 to 5.7 s (originals) and 67 to 9 s (previews); the 33-scene split is estimated at ~3 min (originals) or ~8 min (previews) at `%8`, to be confirmed on the cluster.

A cluster dataset prepares as a Slurm job array, one 1-CPU task per scene, at most N at once (`--array=0-N%throttle`; "Scenes at once" is editable in the preview and changes its hash). Tasks start as single CPUs free up instead of waiting for a multi-CPU allocation, and no CPU idles in the last wave. The claim and lock logic, the preview script with its hash, and the single confirm are kept; `dataset.json` is now also guarded by an atomic `mkdir` lock (tasks run on several nodes, where `flock` may be node-local), and a claim records `<array job>_<task>`. The app follows the array as running while any task runs and as failed if any task failed. A profile (`scripts/bench/prepare_profile.py`, `docs/datasets/prepare-profile.md`) found the ASCII PCD parse was 65 % of a scene's time; it now uses numpy's parser with the same bytes (originals 4.87 → 3.87 s, previews 11.1 → 9.4 s per synthetic scene). These are CPU costs on synthetic data only: the real 33-scene prepare took 1 h 40 min on the cluster, and real timings are still being measured, so the slow prepare is not yet explained or fixed.

Viewing a prepared cluster dataset runs no Slurm job. The app's own viewer server reads the scenes over one long-lived SSH connection to `coperceive dataset stream` (capability `cluster-datasets-5`), a read-only streamer confined to the dataset's cache split and raw root (`realpath` checks; `..`, absolute paths and symlinks out are refused; nothing is written). Requests are pipelined on that one connection; small files are mirrored, sweeps and images are read as byte ranges, prefetched, and kept in a local cache capped at 2 GB (Settings → Cluster datasets → "Viewing cache", "Clear cache"). Ready scenes are viewable while a prepare job runs and when no job can be submitted. Over a 20–40 ms link (25–50 MB/s) a 2-agent OPV2V scene plays at 9.7–9.9 fps the first time with no "Buffering…" frames, and at 10 fps from the cache (`scripts/bench/remote_view_bench.py`). The sweep transform to world coordinates is vectorised (57 ms → 1 ms per 56k-point sweep, bit-identical). The dataset view no longer mentions a viewer job.

A submitted prepare job is followed until it ends, so a scene reads Queued (job N) → Preparing → Ready and "Start preparation & view" opens the viewer when it is ready (polling used to stop at once, before the job reached the scene); a job that ends without preparing is reported. The prepare scripts are shown in full-height, resizable boxes, the cache path comes from the index instead of waiting for a preview, and the viewer window is named after the scene it shows.

Viewing a cluster dataset reuses its viewer job, and the viewer walks the whole dataset. Every Open used to submit a new Slurm serve job; now the first Open of a dataset starts one and every other scene of it goes to the running job and the open viewer (`#/viewer?scene=…`), with a reattach after an app restart. While the job queues, the dataset view says "Starting viewer on the cluster (job N, reason)", and the viewer shows the job and its time left. The viewer's scene menu lists every scene of the dataset with its state; choosing one that is not prepared offers "Prepare & open", confirmed in the main window. |◀ ▶| and the P/N keys move between prepared scenes (`[`/`]` stay speed). A finished scene shows "Scene finished · View next scene (N)"; Settings → "Continue to the next scene automatically" (off by default) plays on, skipping scenes that are not prepared and saying so.

Cluster scenes show their camera images, in the mode you choose. Prepared OPV2V/V2XSet scenes recorded image paths relative to the raw dataset, which the viewer server could not serve ("no camera images staged"). Each prepared scene now has a `raw` link to the dataset root and the viewer server for a cluster dataset is started with that root (exactly) as its media root. `dataset prepare --images originals` (default) reads the dataset's own PNGs and writes nothing extra; `--images previews` also writes a 640 px JPEG per camera frame into the cache (about 38 KB each, ~1.3 GB for a 16-scene split) and loads the full-resolution original when one camera is opened. The prepare preview offers both, with the previews disk estimate, and the choice is part of the script and its hash. Settings → Cluster datasets sets the default per server (or for every server), shows the disk the previews use and removes them after a confirmation; scenes stay viewable from the originals. Switching a prepared scene's mode only re-stages its images. Nothing is ever written under the raw root; a recorded path with `..`, or a link in the dataset that leads out of it, is refused. Settings rows now share one layout: the checkbox or radio on the left, aligned with the title, the description under it.

Playback over a slow link keeps the lidar with the boxes. Over the SSH tunnel a sample's point clouds took longer than the 100 ms sample gap; each one was dropped as stale when the next sample came, while the boxes were redrawn from the newer frame, so points froze where playback started and boxes moved on. Now a frame becomes "the frame on screen" only when its points are applied, together with its boxes; playback holds on a sample until it is drawn and says "Buffering…" while the link is behind; and the status line gives point and box counts only for the sample on screen. The viewer log (`window.__COPERCEIVE_FRAME_STATS__`) records each sample's frame and point fetch times and whether it was applied or dropped. A browser test plays a scene whose points come through a one-at-a-time, 300 ms pipe and asserts the points and boxes show the same sample on every rendered frame.

Cluster datasets index the split you chose. `dataset index` and `dataset prepare` take `--split` (capability `cluster-datasets-3`); a dataset root holding several splits without one is refused with a plain error listing them, where it used to index or prepare the first present (train, when the banner said test). The desktop passes detect's split to index and prepare, and the Dataset view titles itself from the index document. `dataset detect` lists only the split directory and a few scenes' agent folders (a 16-scene synthetic split: 9,916 stats → 53), adapter file discovery takes entry types from one directory listing instead of a stat per frame file, and index's fallback size walk now stops at `--timeout`.

Cluster datasets on real OPV2V/V2XSet. Per-frame records with numpy-tagged scalars (`numpy.core.multiarray.scalar`, `numpy.dtype`, `_reconstruct`) are read as plain numbers by a `SafeLoader` subclass (`coperceive/adapters/readers/numpy_yaml.py`) for `dataset index|prepare` and `adapters check|ingest`; every other `python/*` tag is still refused. `dataset index` lists the other scenes when one scene cannot be read and records it in `errors` (one line); it reads directory listings plus one calibration record per agent instead of building every scene, and walks the tree once (a 16-scene synthetic split: 9.5 s → 1.7 s locally), and `camera_samples`/`lidar_samples` now count every sample rather than the first and last. `dataset detect|index|prepare|status` print a one-line error (traceback with `--verbose`). `coperceive capabilities` reports `cluster-datasets-2`; the desktop dataset commands and Test connection use it to say "coperceive on this server is too old … Update it with: …" instead of argparse output.

Unreleased: Evaluation step B, batch model plugins (ADR 0011, `docs/spec/model-plugin.md`, `docs/models.md`). A model plugin is an entry point under `coperceive.models` or a `--manifest FILE` pointing at a YAML manifest (`spec_version: 1`) and a worker run as a subprocess in its own interpreter (`conda`, `python`, or `current`) over newline-delimited JSON on stdin/stdout with an environment allow-list and secret redaction. Commands: `coperceive model list|inspect|check|run` and `model cache prune`. `model run` drives the plugin over schema 1 scenes, validates boxes, writes a format 1 predictions run with `provenance` (manifest SHA-256, checkpoint path/size/mtime/MD5, GPU model, split timings `staging_s`/`conversion_s`/`inference_s`/`per_sample_s`, dependencies, status `complete` or `partial`), and caches validated scene results under `<run>/cache/<plugin>/<model>/<checkpoint_md5>/<scene>/` (`cache` is now a reserved name in a run directory). Partial runs are evaluated on their finished scenes and marked `partial` in `metrics.json` and `eval report|compare`. Models can declare `depends_on` artefacts (`<run_id>-<model>` or `--artifacts DIR`) and `outputs.transient_artifacts` to keep large intermediate files out of the cache and copy-home step. `model run --slurm` emits an sbatch script that stages only the required scene and raw files to node scratch, times staging, updates time limits from prior provenance, and copies logs and runs home regardless of exit status. The Griffin plugin (`plugins/griffin/`, `coperceive-griffin-model`) exposes `vehicle-side`, `drone-side`, `instance-fusion`, and `early-fusion` for the Griffin-25m release. Live mode (Tasks 9 and 10) stays deferred.

Builtin adapters `opv2v` and `v2xset` (ADR 0012: left-handed sources through one y-reflection, boxes from a location plus a rotated offset with half extents, mapping records, typed discovery, sensors from one per-frame record, a licence block); `coperceive maps identify` names a scene's CARLA town by alignment residual and `adapters ingest --platform-table` applies it; `scripts/opencood/stage_viewer.py`. `scripts/griffin/check_staged_scenes.py` selects each scene from the picker unless the page already shows it, instead of assuming the first scene asked for is the one the page opened on. `maps identify` accepts a town by a relative rule (best at most 0.5 m, runner-up at least 10× the best and 0.5 m worse) instead of a fixed 2 m margin. Schema 1 gains an optional `display_name` per agent, generated at ingest as `<Type> <n>` in ascending raw-id order within each type (`Vehicle 1`, `Drone 1`, `RSU 1`); the page shows it in the agent list, telemetry, camera strip and split view with the raw id as a tooltip and in the selected-box card, and falls back to the raw id without it. The split view's lidar overlay projects only the camera's own agent's sweep, drops points behind the camera or closer than 1 m, colours by depth (warm near, cool far) and draws 1.6 px squares; the 3D legend lists the agent types the scene has (Vehicle, Drone, RSU, Agent) and Lane.

Evaluation step A. Model predictions live in a sidecar root, `<predictions root>/<run_id>/run.json` and `<scene_id>/boxes.parquet`, next to schema 1 scenes, which stay unchanged. `coperceive predictions import` reads JSON lines or Parquet, checks every row against its scene before writing, and `coperceive.evaluation.predictions.write_run` does the same for a training script. `coperceive eval run` places every box in the world frame, matches each `(agent, source)` output to that agent's ground truth per sample and per category, BEV IoU at 0.5 and 0.7 by default or centre distance by config, and writes `matches.parquet` (one row per prediction and per ground-truth box with status, pair, errors and the cooperative columns) and `metrics.json` (per-sample counts, totals, AP per threshold per category, true-positive errors, `recovered`, `lost_by_fusion`, `only_other_agent`, `nobody`, with the config copied in). `eval report` and `eval compare` print one Markdown table with an `all` row and `b − a` deltas. Phase 4 validation. `coperceive validate` writes a JSON report and a Markdown report for a directory of schema 1 scenes: time sync, UAV height above the vehicle, pose speed and acceleration, shared-track and nearest-centre agreement, coverage, and scene and frame counts against the toolkit figures. Phase 1 scene model and schema 1 hybrid store. The contract is `docs/spec/format.md`.

- Agent types `vehicle`, `uav`, `infrastructure`, `other`, plus a string platform map.
- Sensors `camera`, `lidar`, `radar` with `body ← sensor` and an optional camera pinhole.
- Boxes carry a class, an optional track id, an optional visibility, and a `body` or `world` frame.
- `T(dst ← src, t)` covers world, body, and sensor. No default gap. No silent extrapolation.
- Per-agent time queries report `dt_us` for `exact`, `nearest`, `backward`, and `forward`.
- Scene objects are exactly the track ids shared by two or more agents that agree on one class.
