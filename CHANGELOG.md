# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- Viewer styles (Settings → Viewer → Style): Classic (today's layout, the default), Studio, Instrument and Cinema, each a live preview of one scene. The choice is stored in state.json and applies at once. Cinema's camera drift shows only for Cinema and stays off when the system asks for reduced motion. Boxes can be coloured by who recorded them (both, ego only, the other agent) only when that dataset stores each agent's own list and a shared track id: OPV2V (`vehicles`), V2V4Real (`vehicles`) and Griffin (per-agent `track_id`). V2XSet, DAIR-V2X-C, generic scenes and the demo hide it.
- Native installers across three operating systems (PR #134): Windows NSIS installer (`.exe`) with silent `/S` install and uninstall, Linux Debian package (`.deb`) and standalone AppImage, and macOS Apple Silicon (`arm64`) and Intel (`x86_64`) disk images (`.dmg`). The bundled Python standalone runtime is bundled and verified across all four targets. The Intel Mac build is cross-compiled on Apple Silicon runners and verified under Rosetta 2 emulation, but remains untested on physical Intel Mac hardware until verified by a user.
- V2V4Real 10 Hz playback and optional camera manifests (PR #132): V2V4Real streams and plays at 10 Hz (0.1 s per frame), and camera records are marked optional so LiDAR-only manifests validate and play cleanly without requiring phantom camera files.
- Windows and Linux platform behaviour (PR #129): native window decorations, Ctrl shortcut accelerator menu, dynamic reveal labels ("Show in Explorer", "Show in folder", "Show in Finder"), Windows OpenSSH support with `%USERPROFILE%\.ssh\config` and `ControlMaster=no`, process pause and resume via `ntdll.dll` on Windows, strict Windows ACL checks for token and state files, and pure Rust `zip` crate for diagnostics export.
- V2V4Real LiDAR-only release confirmation and box angle keys in degrees `[roll, yaw, pitch]` (PR #131).
- Dataset adapters for V2V4Real and DAIR-V2X-C with automated detection (PR #126). V2V4Real supports LiDAR point clouds and poses in OpenCOOD layout with unverified coordinate convention warnings; DAIR-V2X-C adds support for cooperative infrastructure-vehicle setups.
- CARLA town road maps one-click download and verification in viewer and settings (PR #128), covering two verification classes: towns verified against the official CARLA 0.9.15 package (Town03, Town06, Town07, Town10HD) and towns matching public mirrors without package verification (Town01, Town02, Town04, Town05).
- Cross-platform desktop foundation for Windows and Linux targets (PR #122).
- Automated CI test matrix and headless smoke test pipelines for `ubuntu-latest` and `windows-latest`.
- Push CI trigger support on `release/**` branches for integration testing.

### Changed
- Python 3.10 is no longer supported; the minimum version is 3.11 because Pillow 13 dropped 3.10 (PR #130). Note that the released v0.1.0 app already bundled Pillow 13.0.0.
- Tauri desktop dependencies and build configuration are no longer macOS-only.
- System log directories, application data directories, and clipboard interactions abstracted into platform-specific implementations.

### Fixed
- Diagnostics reporting and zip bundle export made cross-platform with clipboard fallback and clear missing-tool errors.
- Release asset packaging tightened to copy only exact application bundle and DMG assets, excluding stray dependencies.

### Security
- Upgraded Pillow to 13.0.0 in `uv.lock` and tokio to 1.54.1 (PR #130).
- Restricted Pillow image decoders strictly to PNG and JPEG to reduce parser attack surface (PR #130). Note that the released v0.1.0 app already bundled Pillow 13.0.0.

## [0.1.0] - 2026-11-05

### Added
- Native desktop application for macOS (Apple Silicon) built with Tauri and React.
- Dense, calm user interface matching the redesigned layout across Library, Get Data, Servers, and Dataset View.
- HPC Cluster Workspace: SSH remote directory browser, Slurm batch job array preparation, and live cluster job monitoring.
- Zero-Slurm-job cluster dataset viewing over long-lived SSH streaming pipe (`coperceive dataset stream`).
- Interactive 3D scene viewer with lidar point cloud playback, 3D bounding boxes, camera frustums, and multi-agent tracking.
- Multi-agent camera filmstrip with scrolling thumbnails, active-camera split view, and depth-colored lidar point projection.
- Offline and local dataset inspection, validation, and conversion for OPV2V, V2XSet, and Griffin datasets.
- Privacy-preserving crash capture and user-initiated diagnostics dialog with automated secret redaction (preview, clipboard copy, zip bundle export).
- In-app update notifications via sidebar card with release notes popover and restart-to-install workflow.

### Changed
- Redesigned scene viewer and dataset view layout to eliminate element overlap at all window sizes down to 900 × 600.
- Unified window toolbar on macOS with inline traffic light controls.
- Optimized cold raw file reads and YAML parsing during Slurm dataset preparation.

### Fixed
- Prevented point cloud and bounding box desynchronization during playback over high-latency SSH connections.
- Fixed camera frustum image plane poses to stay synchronized with moving agent poses.
- Fixed concurrent remote viewer start conflicts when sharing remote manifests.

Camera image planes follow their agent. With camera images shown in the 3D view, a camera's image plane was posed only after its image loaded, and every frame change cancelled the pending load. Over the SSH link, where an image takes longer than the 100 ms sample gap, the plane stayed at an earlier sample's pose while the ego, boxes and frustum lines moved on. Each plane is now posed in the same draw as its frustum lines, as agent pose(t) × camera mount, for every agent with a camera. A late image is still shown (the closest to the drawn sample wins). A camera with no pose or no image at a sample hides its plane: the frame document's frustums now say `has_image`. Hiding an agent now also hides its image planes; the lookup split the camera key on ":" while keys are "agent/sensor".

The remote viewer page is no longer uploaded again when two sessions start at the same moment. Each start fetched the remote cache's manifest into a temporary file named from the process id and the clock, and macOS clocks tick in whole microseconds, so two starts could share one file: one deleted the other's fetched manifest, which then looked like a missing cache. Temporary names now carry a per-process counter. This also made `remote_static::tests::uploads_once_then_skips_a_complete_cache` fail now and then, because the cache tests run in parallel in one process.

Prepare reads raw files the way the cluster's shared filesystem needs. Real timing (job 670409, one V2XSet scene) showed cold reads at ~150 ms per file (6.4 files/s; 800 MiB/s warm): ~11 min of waiting against ~2 min of CPU, which the old sequential reader paid file by file. Each prepare task now reads its records and sweeps 16 at a time ahead of the parser (`COPERCEIVE_IO_THREADS`, set in the script), in the order the build consumes them; camera previews are read and encoded 16 at a time; each per-frame record is parsed once instead of twice (poses and boxes); "Read originals" opens no PNG (verified). The YAML loader warns when libyaml is missing. Every scene writes a timing line (read wait, build, write, previews, CPU, files, YAML loader) to the job log and to `<cache>/.timing.jsonl`; the prepare preview shows an estimated wall time from the scenes' raw file count, or from the last run's timing log when there is one, and says the shared filesystem is the limit. The default "Scenes at once" is a filesystem budget (8 tasks × 16 reads). With a simulated 150 ms per cold file, a synthetic scene went from 32.6 to 5.7 s (originals) and 67 to 9 s (previews); the 33-scene split is estimated at ~3 min (originals) or ~8 min (previews) at `%8`, to be confirmed on the cluster.

A cluster dataset prepares as a Slurm job array, one 1-CPU task per scene, at most N at once (`--array=0-N%throttle`; "Scenes at once" is editable in the preview and changes its hash). Tasks start as single CPUs free up instead of waiting for a multi-CPU allocation, and no CPU idles in the last wave. The claim and lock logic, the preview script with its hash, and the single confirm are kept; `dataset.json` is now also guarded by an atomic `mkdir` lock (tasks run on several nodes, where `flock` may be node-local), and a claim records `<array job>_<task>`. The app follows the array as running while any task runs and as failed if any task failed. A profile (`scripts/bench/prepare_profile.py`, `docs/datasets/prepare-profile.md`) found the ASCII PCD parse was 65 % of a scene's time; it now uses numpy's parser with the same bytes (originals 4.87 → 3.87 s, previews 11.1 → 9.4 s per synthetic scene). These are CPU costs on synthetic data only: the real 33-scene prepare took 1 h 40 min on the cluster, and real timings are still being measured, so the slow prepare is not yet explained or fixed.

Viewing a prepared cluster dataset runs no Slurm job. The app's own viewer server reads the scenes over one long-lived SSH connection to `coperceive dataset stream` (capability `cluster-datasets-5`), a read-only streamer confined to the dataset's cache split and raw root (`realpath` checks; `..`, absolute paths and symlinks out are refused; nothing is written). Requests are pipelined on that one connection; small files are mirrored, sweeps and images are read as byte ranges, prefetched, and kept in a local cache capped at 2 GB (Settings → Cluster datasets → "Viewing cache", "Clear cache"). Ready scenes are viewable while a prepare job runs and when no job can be submitted. Over a 20–40 ms link (25–50 MB/s) a 2-agent OPV2V scene plays at 9.7–9.9 fps the first time with no "Buffering…" frames, and at 10 fps from the cache (`scripts/bench/remote_view_bench.py`). The sweep transform to world coordinates is vectorised (57 ms → 1 ms per 56k-point sweep, bit-identical). The dataset view no longer mentions a viewer job.

Fixes from the V2XSet acceptance run. A viewer job that Slurm already ran but that had not written its session file yet was reported as "stopped" (state RUNNING) and the app refused it ("Cannot reattach … not running"); `remote status` now calls an active job starting, "running" means reachable, and the app attaches using the job id and the reply's address, waiting while the job starts (also with an older CLI). A whole-dataset prepare opens the viewer on the first scene it makes ready (Settings → "Open the viewer when the first scene is ready", on by default); the rest appear in the viewer's scene menu as they finish. Tabs (and the HPC workspace's sections) stay mounted once shown, so an open dataset survives a visit to Get Data, and the last open dataset per server is reopened after a restart. A jobs indicator in the top bar lists the datasets being prepared ("15 ready · 3 preparing · 15 queued", job ids, viewer open or closed), opens one on click, and says when a dataset finishes. The camera-image choice in a prepare preview changes at once; the script box says "Updating preview…" and Submit waits for the new script.

Both windows use a unified toolbar on macOS: no native title bar, the traffic lights inline at the left of the app's own top bar. Empty toolbar space moves the window and double-click zooms it; the toolbar keeps clear of the traffic lights at any width and gives the space back in full screen. The viewer window may only move and zoom itself (its own capability); it gains no other command.

The viewer offers only what a scene has. Its views come from the scene's own data, never from the dataset's name: Drone needs a UAV and a vehicle, Chase a vehicle, Camera a calibrated camera; the Frustums layer needs a camera. A Griffin scene keeps Drone; OPV2V and V2XSet scenes no longer show it. When the next scene lacks the active view, the viewer falls back to Orbit without an error, and a shortcut for a view the scene lacks does nothing.

The dataset view leads with the whole dataset and follows its jobs. With nothing prepared it offers "Prepare whole dataset (~X GB, 1 CPU job)" first (same preview, camera-image choice and confirm; single-scene Prepare & open stays below) and says so once every scene is ready. A submitted prepare job is followed until it ends, so a scene reads Queued (job N) → Preparing → Ready and "Start preparation & view" opens the viewer when it is ready (polling used to stop at once, before the job reached the scene); a job that ends without preparing is reported. The prepare scripts are shown in full-height, resizable boxes, the cache path comes from the index instead of waiting for a preview, and the viewer window is named after the scene it shows.

Viewing a cluster dataset reuses its viewer job, and the viewer walks the whole dataset. Every Open used to submit a new Slurm serve job; now the first Open of a dataset starts one and every other scene of it goes to the running job and the open viewer (`#/viewer?scene=…`), with a reattach after an app restart. While the job queues, the dataset view says "Starting viewer on the cluster (job N, reason)", and the viewer shows the job and its time left. The viewer's scene menu lists every scene of the dataset with its state; choosing one that is not prepared offers "Prepare & open", confirmed in the main window. |◀ ▶| and the P/N keys move between prepared scenes (`[`/`]` stay speed). A finished scene shows "Scene finished · View next scene (N)"; Settings → "Continue to the next scene automatically" (off by default) plays on, skipping scenes that are not prepared and saying so.

Cluster scenes show their camera images, in the mode you choose. Prepared OPV2V/V2XSet scenes recorded image paths relative to the raw dataset, which the viewer server could not serve ("no camera images staged"). Each prepared scene now has a `raw` link to the dataset root and the viewer server for a cluster dataset is started with that root (exactly) as its media root. `dataset prepare --images originals` (default) reads the dataset's own PNGs and writes nothing extra; `--images previews` also writes a 640 px JPEG per camera frame into the cache (about 38 KB each, ~1.3 GB for a 16-scene split) and loads the full-resolution original when one camera is opened. The prepare preview offers both, with the previews disk estimate, and the choice is part of the script and its hash. Settings → Cluster datasets sets the default per server (or for every server), shows the disk the previews use and removes them after a confirmation; scenes stay viewable from the originals. Switching a prepared scene's mode only re-stages its images. Nothing is ever written under the raw root; a recorded path with `..`, or a link in the dataset that leads out of it, is refused. Settings rows now share one layout: the checkbox or radio on the left, aligned with the title, the description under it.

Playback over a slow link keeps the lidar with the boxes. Over the SSH tunnel a sample's point clouds took longer than the 100 ms sample gap; each one was dropped as stale when the next sample came, while the boxes were redrawn from the newer frame, so points froze where playback started and boxes moved on. Now a frame becomes "the frame on screen" only when its points are applied, together with its boxes; playback holds on a sample until it is drawn and says "Buffering…" while the link is behind; and the status line gives point and box counts only for the sample on screen. The viewer log (`window.__COPERCEIVE_FRAME_STATS__`) records each sample's frame and point fetch times and whether it was applied or dropped. A browser test plays a scene whose points come through a one-at-a-time, 300 ms pipe and asserts the points and boxes show the same sample on every rendered frame.

Cluster datasets index the split you chose. `dataset index` and `dataset prepare` take `--split` (capability `cluster-datasets-3`); a dataset root holding several splits without one is refused with a plain error listing them, where it used to index or prepare the first present (train, when the banner said test). The desktop passes detect's split to index and prepare, and the Dataset view titles itself from the index document. `dataset detect` lists only the split directory and a few scenes' agent folders (a 16-scene synthetic split: 9,916 stats → 53), adapter file discovery takes entry types from one directory listing instead of a stat per frame file, and index's fallback size walk now stops at `--timeout`.

Cluster datasets on real OPV2V/V2XSet. Per-frame records with numpy-tagged scalars (`numpy.core.multiarray.scalar`, `numpy.dtype`, `_reconstruct`) are read as plain numbers by a `SafeLoader` subclass (`coperceive/adapters/readers/numpy_yaml.py`) for `dataset index|prepare` and `adapters check|ingest`; every other `python/*` tag is still refused. `dataset index` lists the other scenes when one scene cannot be read and records it in `errors` (one line); it reads directory listings plus one calibration record per agent instead of building every scene, and walks the tree once (a 16-scene synthetic split: 9.5 s → 1.7 s locally), and `camera_samples`/`lidar_samples` now count every sample rather than the first and last. `dataset detect|index|prepare|status` print a one-line error (traceback with `--verbose`). `coperceive capabilities` reports `cluster-datasets-2`; the desktop dataset commands and Test connection use it to say "coperceive on this server is too old … Update it with: …" instead of argparse output.

Unreleased: Evaluation step B, batch model plugins (ADR 0011, `docs/spec/model-plugin.md`, `docs/models.md`). A model plugin is an entry point under `coperceive.models` or a `--manifest FILE` pointing at a YAML manifest (`spec_version: 1`) and a worker run as a subprocess in its own interpreter (`conda`, `python`, or `current`) over newline-delimited JSON on stdin/stdout with an environment allow-list and secret redaction. Commands: `coperceive model list|inspect|check|run` and `model cache prune`. `model run` drives the plugin over schema 1 scenes, validates boxes, writes a format 1 predictions run with `provenance` (manifest SHA-256, checkpoint path/size/mtime/MD5, GPU model, split timings `staging_s`/`conversion_s`/`inference_s`/`per_sample_s`, dependencies, status `complete` or `partial`), and caches validated scene results under `<run>/cache/<plugin>/<model>/<checkpoint_md5>/<scene>/` (`cache` is now a reserved name in a run directory). Partial runs are evaluated on their finished scenes and marked `partial` in `metrics.json` and `eval report|compare`. Models can declare `depends_on` artefacts (`<run_id>-<model>` or `--artifacts DIR`) and `outputs.transient_artifacts` to keep large intermediate files out of the cache and copy-home step. `model run --slurm` emits an sbatch script that stages only the required scene and raw files to node scratch, times staging, updates time limits from prior provenance, and copies logs and runs home regardless of exit status. The Griffin plugin (`plugins/griffin/`, `coperceive-griffin-model`) exposes `vehicle-side`, `drone-side`, `instance-fusion`, and `early-fusion` for the Griffin-25m release. Live mode (Tasks 9 and 10) stays deferred.

Builtin adapters `opv2v` and `v2xset` (ADR 0012: left-handed sources through one y-reflection, boxes from a location plus a rotated offset with half extents, mapping records, typed discovery, sensors from one per-frame record, a licence block); `coperceive maps identify` names a scene's CARLA town by alignment residual and `adapters ingest --platform-table` applies it; `scripts/opencood/stage_viewer.py`. `scripts/griffin/check_staged_scenes.py` selects each scene from the picker unless the page already shows it, instead of assuming the first scene asked for is the one the page opened on. `maps identify` accepts a town by a relative rule (best at most 0.5 m, runner-up at least 10× the best and 0.5 m worse) instead of a fixed 2 m margin. Schema 1 gains an optional `display_name` per agent, generated at ingest as `<Type> <n>` in ascending raw-id order within each type (`Vehicle 1`, `Drone 1`, `RSU 1`); the page shows it in the agent list, telemetry, camera strip and split view with the raw id as a tooltip and in the selected-box card, and falls back to the raw id without it. The split view's lidar overlay projects only the camera's own agent's sweep, drops points behind the camera or closer than 1 m, colours by depth (warm near, cool far) and draws 1.6 px squares; the 3D legend lists the agent types the scene has (Vehicle, Drone, RSU, Agent) and Lane.

Evaluation step A. Model predictions live in a sidecar root, `<predictions root>/<run_id>/run.json` and `<scene_id>/boxes.parquet`, next to schema 1 scenes, which stay unchanged. `coperceive predictions import` reads JSON lines or Parquet, checks every row against its scene before writing, and `coperceive.evaluation.predictions.write_run` does the same for a training script. `coperceive eval run` places every box in the world frame, matches each `(agent, source)` output to that agent's ground truth per sample and per category, BEV IoU at 0.5 and 0.7 by default or centre distance by config, and writes `matches.parquet` (one row per prediction and per ground-truth box with status, pair, errors and the cooperative columns) and `metrics.json` (per-sample counts, totals, AP per threshold per category, true-positive errors, `recovered`, `lost_by_fusion`, `only_other_agent`, `nobody`, with the config copied in). `eval report` and `eval compare` print one Markdown table with an `all` row and `b − a` deltas. The page gains three read-only routes under `/api/scenes/{id}/predictions`, a `--predictions` root on `serve`, a Predictions block with run, compare and output selectors, source, status and cooperative chips, a score slider and a legend, status wires in teal, amber and violet with solid, dashed and dotted lines, inspector fields, timeline sparklines for precision, recall and FP, and mAP, recall and the cooperative counts on the scene card. `coperceive export bev --run` and the bird's-eye POST draw the same rows. Only synthetic fixtures have been evaluated; `tests/test_eval_end_to_end.py` runs the chain from JSON lines to the compare table. The user page is `docs/eval.md`, the contract is `docs/spec/predictions.md`, the design is `docs/adr/0010-eval-predictions.md`.

Dataset adapters. A YAML manifest describes a dataset's layout, readers, units, rotation encodings and axis conventions, and `coperceive adapters list|check|ingest` turns the raw tree into schema 1 scenes with the same parallel driver, `.partial/` directory and `COMPLETE.json` resume that Griffin used. Generic readers: JSON, YAML and CSV records, joined JSON tables, whitespace label rows, PLY, PCD and float32 BIN lidar, image folders. Plugins register under the `coperceive.adapters` and `coperceive.readers` entry points. Griffin ships as the built-in manifest `coperceive/adapters/builtin/griffin.yaml`; `tests/test_adapters_griffin.py` checks it writes byte-identical `points.bin`, equal Parquet tables and equal scenes against the pre-adapter converter, now frozen in `tests/griffin_reference.py`; after that test passed on the real Griffin-25m release, `coperceive convert griffin` became a permanent alias for the adapter with the same report and output. `COMPLETE.json` records the adapter, the manifest SHA-256 and the coperceive version. The body (`FLU`) and camera (`RDF`) axis conventions are written into `docs/spec/format.md`; schema 1 is unchanged. `pyyaml` is a dependency. The walkthrough is `docs/datasets/add-a-dataset.md` and the design is `docs/adr/0009-dataset-adapters.md`.

Web UI. The page opens on a landing view, then the viewer. The top bar is one 32 px row: brand and scene, Viewer/Desk, then Export, theme, and settings. The right column adds a scene summary, a box inspector, and an 80 m radar. Camera frustum images start off. Each camera can be turned on from the layer list, its picture-in-picture chip, or a click on the frustum, and only those frames are decoded. Phase 4 validation. `coperceive validate` writes a JSON report and a Markdown report for a directory of schema 1 scenes: time sync, UAV height above the vehicle, pose speed and acceleration, shared-track and nearest-centre agreement, coverage, and scene and frame counts against the toolkit figures. Speed above 40 m/s and acceleration above 20 m/s² are warnings. A 0.5 s trailing mean of speed is the smoothed acceleration check. The computed-pair gate is `max(2 m, 0.5 * the longer box length)` and stays labelled computed. The default exit is 0. `--strict` exits 1 on an unreadable scene, a missing frame, or a cross-agent pose miss. The Griffin-25m dev-tier numbers are in `docs/validate.md`.

CI installs the CPU torch wheel and typechecks `CooperativeDataset`. The Griffin licence acknowledgement uses `timezone.utc`, which Python 3.10 provides. `datetime.UTC` does not exist there.

Phase 3 cooperative queries. `Scene.at` returns every agent's pose, sensors, and boxes at one time, with per-agent `dt_us`. A miss is reported. Camera projection uses the pinhole and the rigid extrinsic, and reports behind-camera and out-of-image points without rounding. Cross-agent box queries label a distance match as computed, not ground truth, when the track id is not a shared object. `CooperativeDataset` is the `torch` extra: configurable agents, sensors, and sampling, with a per-worker lazy open.

Phase 2 Griffin download and conversion. `coperceive download griffin` fetches a subset from `wjh-svm/Griffin`. `coperceive convert griffin` writes one schema 1 scene for the vehicle and the drone. Conventions are in `docs/datasets/griffin.md`.

Phase 1 scene model and schema 1 hybrid store. The contract is `docs/spec/format.md`.

- Agent types `vehicle`, `uav`, `infrastructure`, `other`, plus a string platform map.
- Sensors `camera`, `lidar`, `radar` with `body ← sensor` and an optional camera pinhole.
- Boxes carry a class, an optional track id, an optional visibility, and a `body` or `world` frame.
- `T(dst ← src, t)` covers world, body, and sensor. No default gap. No silent extrapolation.
- Per-agent time queries report `dt_us` for `exact`, `nearest`, `backward`, and `forward`.
- Scene objects are exactly the track ids shared by two or more agents that agree on one class.

Phase 0 scaffold. The distribution, import, and command name are `coperceive`.

- Scene model, time queries, and `T(dst ← src, t)` with explicit interpolation limits.
- Hybrid Parquet plus float32 point blob.
- Griffin-25m reader and an allow-listed downloader for metadata and vehicle LiDAR.
- Local FastAPI app and a prebuilt browser page.
- Design notes and measurements. No training code.
